2. Kernel IR (Body) Structure

Body

One kernel function: name, params, locals, basic blocks, workgroup_size, LDS declarations.

  • params: ptr addrspace(1) + i64 len per slice
  • locals: typed registers (f32, bf16, i32, usize, bool, i32 fragments)
  • workgroup_size: e.g., [32, 1, 1] for one wave
  • workgroup_locals: LDS arrays (addrspace 3)

BasicBlock

Sequence of Statements ending with a Terminator.

  • Statements: Assign, WmmaLoad, WmmaMma, WmmaStore, WmmaLoadLds
  • Terminators: Goto, SwitchInt, ThreadIndexCall, Barrier, Return
  • Rvalues: BinaryOp, UnaryOp, MathUnary, Cast, Bitcast, SubgroupReduce

WMMA Ops

Tensor core operations in the kernel IR.

  • WmmaLoad { which: A|B, tile, stride, dst: [Local; 8] }
  • WmmaMma { a, b, c, dst: [Local; 8] }
  • WmmaStore { tile, stride, src: [Local; 8] }
  • 8 VGPRs for fragments, same IR for all backends

4. The WMMA Fragment Layout Problem

This is the key architectural difference between PTX and AMDGPU. On PTX, the LLVM intrinsics handle memory-to-fragment mapping. On AMDGPU, we must do it ourselves.

6. Graph Execution Modes

Vulkan / wgpu

  • G1: Host round-trip (every value uploaded/downloaded)
  • G4: Device-resident, cached re-encode (one submit per token)
  • Pipeline cache: in-memory -> disk -> llc compile
  • Bind groups from KernelBuffer slices
  • Grid cap: 65535 per dimension

NVIDIA / CUDA

  • G3: Eager per-dispatch (cuLaunchKernel)
  • G3c: CUDA Graph capture/replay (one cuGraphLaunch per token)
  • Cooperative grid support
  • No grid cap (2^31-1)

AMD / HSA

  • Per-dispatch AQL packets
  • Batched replay: capture AQLs, replay with single doorbell per token
  • Strix Halo: 1 workgroup per AQL packet
  • Multi-block: N AQL packets with pointer offsets
  • KD (kernel descriptor) patching at load time

Device libs None needed None needed (PTX is virtual) ROCm device-libs (ockl, oclc_*) required
Post-processing Barrier SeqCst -> AcquireRelease None (CUDA JIT handles it) KD ENABLE_SGPR patching
Runtime loader wgpu (Vulkan driver) CUDA driver (cuModuleLoadData) HSA runtime (hsa_executable_load)
The ROCm path requires amdclang (not bare llc) because: bare llc -filetype=obj produces a relocatable without the PT_AMDGPU_HSA_LOAD_GLOBAL_DATA / PT_AMDGPU_HSA_LOAD_KERNEL_ARGUMENT program headers that the HSA runtime needs. Additionally, amdclang auto-links ROCm device-libs (ockl, oclc_isa_version_1151, etc.) which provide implementations for things like __ocml_exp_f32.

8. Key Differences Summary

What's shared across all backends

  • Graph IR (OpKind, Eqn, TensorType)
  • Graph optimization (CSE, fusion, DCE)
  • Kernel IR (Body, BasicBlock, Statement)
  • Planning (plan_eqn_analyzed, imported vs synthesized)
  • ~80% of LLVM IR emission
  • Model definitions, checkpoint loading, serving

What's per-backend

  • Target triple, pointer types, usize width
  • Thread ID, barrier, LDS intrinsics
  • WMMA: PTX has 3 intrinsics, AMD has 1, Vulkan has 0
  • Fragment layout: PTX opaque, AMD manual, Vulkan N/A
  • Compiler tool: llc vs amdclang
  • Post-processing: barrier fix, KD patch, device-libs
  • GPU dispatch API: wgpu / CUDA / HSA
  • Capture/replay mechanism
