# Feature matrix

The `poot-llm` library selects a GPU runtime with `--backend`. **Three production backends** run the
same graph IR today: **wgpu** (Vulkan/SPIR-V, default), **rocm** (AMD raw HSA), and **ptx** (NVIDIA).
They are not at parity. A fourth backend, raw Vulkan, has its own section below and is not a column in
these tables.
This page answers "does X work on backend Y?". The model and weight-format tables are generated from what the
planner says; the other tables are written by hand.

The AMD XDNA2 and Intel NPU4 NPUs are not columns here: XDNA2 runs only F32 `add`, `sub` and `mul` programs and Intel only a short list of F16 ops (see
[NPU offload](../architecture/npu.mdx)).

For lower-level kernel/dispatch capability (elementwise, GEMV, flash attention, capture/replay, ...), see
the [Backends](../architecture/backends.mdx#capability-comparison) architecture page, this page is the
serving-level view: what `poot-serve` and the `poot-llm` library provide, with the cells that have
no served test marked as such.

Legend: colored badges use the same vocabulary on this page and on
[Backends: capability comparison](../architecture/backends.mdx#capability-comparison).
**Yes** = the indicated path has test coverage; footnotes distinguish format tests from model receipts. **Partial** = works, with scope limits noted.
**No** = not implemented for that backend. **N/A** = the concept does not apply to that backend.

`poot-serve` serves generation (`/v1/completions`, `/v1/chat/completions`), embeddings, reranking and LoRA administration from one engine thread over the driver on wgpu and ROCm. PTX and raw Vulkan serve generation too. See [Serving](../serve/index.md).

## Models and weight formats

Whether a model runs on a backend is decided by planning: a model runs when compiling its graph for that backend
succeeds, and a refusal is a typed error naming the op and the capability the backend lacks. So these tables are not
written by hand. A test compiles the fixture graphs of every registered model family, and a dense model whose
projections are stored in every weight format, for each backend, and writes the result between the markers below.

## Reading the matrix

- **Plans** means every fixture graph of the row compiled for that backend: decode and prefill for a decoder, the one
  forward for an encoder. It says the planner can lower the graph. It does not say a real checkpoint of that family
  has run there; the Measured table lists the stored benchmark rows that did.
- **Refused** carries the shape being compiled, the op, and the capability the backend lacks, exactly as the planner
  reports it. A row is a family key, or `family/variant` for one of the family's option fixtures (a Mixtral or
  Granite MoE checkpoint is the llama or granite family with experts).
- **Rejected** is a compile failure that is not a missing capability, for example a graph over the compile limits.
- The weight-format table binds a random admitted payload of each format as the stored bytes; it checks the
  lowering, not the numbers. A GGUF Mixtral names the `llama` architecture and loads as the llama family with experts
  when its metadata has `llama.expert_count`; a DeepSeek-V3 GGUF names `deepseek2`.
- MXFP4 weights stay packed at load time. The routed-expert projection is one indexed packed contraction that reads
  only the selected experts' blocks; no expert table is materialized. Dense BF16 and F16 weights are kept as stored
  words with no host f32 copy. Packed checkpoint size is not a bound on total peak memory.
- Real checkpoints: Qwen3.8-27B-FP8 ran on PTX (one H100 80 GB) and generates "Paris" for "The capital of France is",
  with the first token's top-five log-probabilities equal to the CPU oracle's within 1e-3. On ROCm (gfx1151) it also
  generates "Paris" with coherent text (about 5 decode tok/s, 12 prefill tok/s); its top-five comparison against the CPU
  oracle has not been run yet. It has not run on wgpu. DeepSeek-V4, MiniMax-M2, GLM-5.3-Flash and Qwen3.8-Flash-Next have only synthetic fixtures that match an
  independent f64 reference; no real public checkpoint of them has run.
- The `bert` family runs on the driver's `Encode` step (`poot_llm::encoders`). `poot-serve` runs `Encode` steps for a
  decoder's embeddings and reranking on wgpu and ROCm, and starts on a BERT checkpoint (embeddings and cross-encoder
  rerank); the encode shapes are fitted and prepared before it serves.
- Per-channel E4M3 `compressed-tensors` projections load packed and use the shared generated lowering. See
  [Using quantized checkpoints](../serve/quantized-checkpoints.md).

## Expert pooling

Expert pooling keeps a fixed number of resident expert rows per MoE layer and makes the experts a step selects
resident before they are read, least recently used rows making room. It is a serving option (`--expert-pool ROWS`,
see [Configuration](../serve/configuration.md)) for a model with routed experts whose stacked tables the planner can
page, with the pool smaller than the expert count and at least the experts one token selects. A prefill longer than
the pool serves is split into smaller chunks by the driver; a decode step whose rows times experts per token exceed
the pool is refused at prepare with a typed capacity error, never split. Without the option every expert's weights
are resident. Pooled decode is verified token for token against the resident run on Mixtral's fixture on wgpu and
ROCm; the PTX run is pending, and the matrix cells above describe the resident paths.

    The scheduling loop and the driver are backend-neutral, but the served tests on PTX cover the dense fixture
    (greedy and sampled) and the SmolVLM caption only. A cell marked "no served test" has not been run through the
    server on PTX. See [Serving](../serve/index.md).

## Precision and execution model

|                                                       | wgpu                                                                                  | ROCm                                                                                          | PTX                                                                                  |
| ----------------------------------------------------- | ------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| Compute dtype                                         | f32                                                                                   | f32, opt-in bf16 tensor-core matmul                                                           | f32, opt-in bf16 tensor-core matmul                                                  |
| Tensor-core / matrix-unit matmul                      | <span class="matrix-status matrix-status--no">No</span>[^wgpu-coopmat]                | <span class="matrix-status matrix-status--yes">Yes</span> (RDNA WMMA, verified gfx1151)       | <span class="matrix-status matrix-status--yes">Yes</span> (NVIDIA WMMA)              |
| Execution model per token                             | Cached command-buffer re-encode + submit                                              | Raw HSA AQL packet record/replay                                                              | CUDA graph capture/replay                                                            |
| Megakernel (on-device token loop, no host round-trip) | <span class="matrix-status matrix-status--no">No</span> (no grid-wide sync primitive) | <span class="matrix-status matrix-status--no">No</span> (removed)[^megakernel-scope]          | <span class="matrix-status matrix-status--no">No</span> (removed)[^megakernel-scope] |
| Requires a vendor SDK / driver beyond Vulkan          | <span class="matrix-status matrix-status--no">No</span>                               | <span class="matrix-status matrix-status--yes">Yes</span> (ROCm/HSA userspace)                | <span class="matrix-status matrix-status--yes">Yes</span> (CUDA)                     |
| On by default                                         | <span class="matrix-status matrix-status--yes">Yes</span>                             | <span class="matrix-status matrix-status--no">No</span> (`--features rocm`, `--backend rocm`) | <span class="matrix-status matrix-status--no">No</span> (`--backend ptx`)            |

[^wgpu-coopmat]:
    A SPIR-V cooperative-matrix matmul exists and is hardware-verified on RDNA3.5 (f16 operands, f32 output,
    16-aligned M/N/K, any batch; the accumulator is carried across K blocks), but no model's matmul feeds it
    yet, so it is not on the hot path for any model today.

[^megakernel-scope]:
    The implementation was removed. The strategy is planned as a recorder behind the one compiled
    program on PTX and ROCm; see [The Megakernel](../architecture/megakernel.mdx).

## Raw Vulkan

Raw Vulkan (`--backend vulkan`) runs the same SPIR-V kernels as wgpu through `ash`, with no wgpu. It implements the
same executor contract as the other backends: a program is recorded once as native Vulkan command buffers and
replayed, so a step costs a submit and a fence wait. It is lower priority than PTX and ROCm and is verified on
one device family.

| Item                                    | Status                                                                                                                                    |
| --------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| Executor parity table                   | <span class="matrix-status matrix-status--yes">Yes</span> (the parity table and the backend-neutral coverage fixtures)                    |
| Dense decoder, greedy decode            | <span class="matrix-status matrix-status--yes">Yes</span> (the registry's qwen2 fixture generates the same tokens as wgpu)                |
| Tensor-core matmul (cooperative matrix) | <span class="matrix-status matrix-status--yes">Yes</span> (needs `VK_KHR_cooperative_matrix` and subgroup-size control; verified RDNA3.5) |
| Device-time profiling                   | <span class="matrix-status matrix-status--no">No</span> (no typed timing mode constructs a raw Vulkan device yet)                         |
| Multi-GPU / collectives                 | <span class="matrix-status matrix-status--no">No</span>                                                                                   |
| Serving                                 | <span class="matrix-status matrix-status--yes">Yes</span> (greedy dense decoder verified; a driver without `VK_EXT_memory_budget` is refused at startup) |
| Hardware verified                       | AMD Strix Halo iGPU under RADV only. NVIDIA and Intel Vulkan drivers are untested.                                                        |

The device reports its own limits (largest buffer, grid, workgroup memory, subgroup sizes and matrix hardware)
from the physical device, and the planner refuses what they rule out with a typed error instead of failing in the
driver.

## How to read this if you are choosing hardware

- **NVIDIA GPU:** PTX has the most mature single-GPU library path. `poot-serve` serves the dense fixture on PTX; see the serving table above for what has a served test.
- **AMD GPU:** ROCm is the primary backend on AMD hardware for single-sequence library decode. wgpu also
  runs on the same AMD GPU as a fully portable fallback.
- **Anything else (Intel iGPU/dGPU, other Vulkan-capable hardware):** wgpu is the supported choice. Raw Vulkan
  runs there in principle but is verified on AMD (RADV) only. Pick either through the `poot-llm` API
  or the `poot-serve` `--backend` option.
- **NPU:** AMD XDNA2 (F32 `add`, `sub`, `mul`) and Intel NPU4 (a short list of F16 ops), experimental, no model. See
  [Architecture: NPU Offload](../architecture/npu.mdx).

See [Picking a backend](../serve/choosing-a-backend.md) for the decision walkthrough.
