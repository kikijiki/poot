<summary>Methodology</summary>

Every number is the median over the repeats of a committed run set; the whiskers are the minimum and maximum of a point measured on one host. These are single-request measurements, not continuous-batching throughput. The standing grid is two machines (the local AMD Strix Halo box and one RTX PRO 6000 Blackwell cloud GPU), five models shown and llama.cpp as the reference; transformers and candle appear only on the bf16 qwen3 rows. A sixth grid model, gpt-oss-20b, is not run: poot cannot load its MXFP4 weights yet. Hardware and models outside the grid are not shown, and a cell the grid requires but has not been run yet is simply absent. Supported families, formats and backends are in [Supported models and formats](../develop/supported-models.md).

**Input tokens.** Rate and latency charts have the number of input tokens on their x axis, every length at once. Memory and energy are one value per run, so they are one bar per framework and backend. A chart appears only when every hardware entry has data for its metric.

- A context sweep prefills 128 to 8192 tokens of synthetic random text (no tokenizer, no prefix cache), then times 128 generated tokens at each length. A short prompt and a prompt of about 1000 tokens are two more points on the same axis.
- Decode tok/s is the rate of the 128 generated tokens. Prefill tok/s is the input tokens divided by the first-token time, stated from 128 input tokens up.
- A decode series only holds runs that generated 128 tokens. The run with a prompt of about 1000 tokens generates 32, so it contributes prefill, first-token time and memory only.
- Time per output token is 1000 divided by the decode rate. End-to-end time is the first-token time plus 128 output tokens.
- A sweep's memory and energy are peaks and totals over every length, drawn as one bar per series.

**Verification.** A cell is five to fifteen repeats. It is verified when every row states a clean release build with its adapter, driver, checkpoint digest and compute dtype, one binary produced all repeats, every identity field agrees, and the noise band is within 10% of the median. The band is of the decode rate, the headline metric, and is twice the noise of the repeats (2.33 robust sigmas at five repeats, narrowing with the square root of the repeat count). The widest band among the latest verified cells is 6.4%, and no latest cell is unverified.

A verified cell is drawn solid. A cell that does not verify is shown only when it is on the reviewed list of known-unverified cells, drawn dashed with hollow markers and labelled "unverified: noisy host". Other failing run sets are not shown.

**Weights.** Every cell of a model runs the same weights: a model that lives in a Hugging Face repository names the revision it was measured on and the download fetches exactly that revision, so a repository re-quantised in place does not change the bytes behind a published number. Flash-Next (the UD-Q2_K_XL quant of `unsloth/Qwen3.8-Flash-Next-GGUF`) is pinned to revision `766911a6b736`, the repository's state before it was re-quantised in place on 2026-11-04; poot and llama.cpp read the same three shards, and every Flash-Next row shown records the revision.

**Page cache.** Before each cell the harness reads the model's whole weights set (every shard of a split GGUF, every file of a checkpoint directory) to the end, so every engine starts from a warm file cache whichever engine ran before it, and the row records the cache state, the files and bytes read and the major page faults of the cell's process tree. A set that is incomplete, unreadable or larger than the memory available to hold it is refused with a typed reason and the cell is not run. A warm repeat that took more than 4096 major faults leaves the cell unverified. This is recent: the cells that predate it record no cache state and are not claimed warm. They are the Strix Halo qwen3-0.6b, qwen3-4b and qwen3-4b-q4km cells of llama.cpp and of poot on Vulkan and wgpu; on the RTX PRO 6000 the candle qwen3-0.6b and transformers qwen3-0.6b and qwen3-4b cells, and the 128- and 8192-token points of qwen3.8-27b-q4. Every other cell, including every poot ROCm and PTX cell except those 27B points, records a warm cache.

**Cooling.** The two Strix Halo Flash-Next cells (poot on ROCm and llama.cpp on Vulkan) were measured with a cooldown before every repeat: a repeat started only once the GPU edge temperature was at or below 65 C and the CPU die at or below 75 C. Those cells run 35 to 40 minutes and, uncooled, the chip heated to 87 to 89 C and its shader clock fell from 2755 to 2470 MHz, so the later repeats slowed. Every other cell was measured without that wait.

**Hardware.** One entry per GPU model; editions of one chip (workstation and server) are one entry, Max-Q is its own. The RTX PRO 6000 Blackwell cells ran on rented cards of both editions: every poot and llama.cpp cell shown ran on a Server Edition card, the candle qwen3-0.6b cell and the transformers qwen3-4b cell on a Workstation Edition card, and the transformers qwen3-0.6b cell on a Server Edition card. The edition matters: on the same software the Server Edition card measured 8 to 15% slower per decoded token on qwen3-4b and its Q4_K_M quant (llama.cpp, candle and poot all moved alike) than the Workstation Edition card did, so a Workstation Edition cell is not directly comparable with a Server Edition cell at that level. A cell still pools repeats only from the same accelerator, host CPU and GPU driver, and the harness verifies it on its own host. A point on several hosts is the median of the per-host medians over the verified cells (all cells, drawn unverified, when none verifies).

**Backends.** Every series names its framework and backend. poot runs record PTX, ROCm, Vulkan or wgpu. The NVIDIA llama.cpp baseline runs from the benchmark image (CUDA) and the AMD llama.cpp rows are a Vulkan build.

**What poot computes.** A dense bf16 safetensors run records compute dtype `f32`: the checkpoint is read as bf16 and computed in f32. Packed GGUF, GPTQ/AWQ and supported FP8 projections stay packed and are decoded by the generated kernels (see [Using quantized checkpoints](../serve/quantized-checkpoints.md)). A quantized run has its own identity and is not comparable to a dense run.

**Request timing.**

- TTFT ends at the first token. TPOT is the mean of all inter-token gaps, including the first. E2E includes the first-token, token-to-token and finish windows.
- Preparing wgpu decode before the first token (pending uploads after a cache build or a request-state reset) counts towards TTFT and E2E.
- Unprofiled wgpu execution groups a submission's dispatches into one compute pass; use unprofiled wall time for latency comparisons.

**Memory.** The memory bars show the peak at inference: the highest host resident set (process tree) and GPU memory in use after the model is loaded and the warmup request has run, so the weights, KV cache and scratch at steady state. Both are derived from the 1 Hz memory trace stored with every run, cut at the end of the load plus the warmup (the engine's recorded open time, or the last load ramp the trace shows; llama.cpp restarts its server per context length, so the last load bounds the window). A run whose trace shows no boundary keeps the peak over the whole process lifetime and its bar says "includes load". GPU memory is shown for runs whose device reports it, minus what the device held before the run. On a unified-memory device the weights count towards the resident set.

**Reproducing.**

```bash
# 5 repeats of one cell on the local backend, then regenerate the index
just bench-record rocm qwen3-0.6b prefill-1k
python3 benchmarks/harness/bench.py index
# regenerate the data of this page
just perf-page-regen
```

`just bench-record <backend> <model> <workload>` takes `decode-128`, `prefill-1k` and `decode-curve`.
`just bench-compare` judges a new set of repeats against the committed one with the harness's noise-aware comparator.
