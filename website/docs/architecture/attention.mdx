# Attention and KV Cache

Naive attention, `softmax(QK^T / sqrtd_k) * V` [^transformer], builds an `[L x L]` score matrix that does not fit in GPU SRAM
for long contexts. poot handles it in three stages: the tracer records primitive ops, a compiler pass fuses them into one
flash attention op, and a KV cache stores past keys and values.

## Attention as primitive ops

`ops::attention_masked` emits about ten primitive eqns, plus the KV write and the GQA repeat. There is no attention opcode.

| Step | Eqns |
| --- | --- |
| KV write | `DynamicUpdateSlice` of k and v into the state buffers at `pos` |
| GQA repeat | `repeat_kv`: `Reshape`, `Broadcast`, `Reshape` (a no-op when `H_q == H_kv`) |
| Scores | `MatMul(q, Transpose(k))`, `Mul` by scale (usually `1/sqrt(D)`), `Add` of the mask |
| Softmax | `Reduce(Max)`, `Sub`, `Exp`, `Reduce(Sum)`, `Div` |
| Output | `MatMul(p, v)` |

The mask is large negative past `pos`; it is a graph computation over `Slot::Pos`. The flash rewrite recognizes this chain.

## Multi-head, GQA, and MQA

Multi-query (MQA) [^mqa] and grouped-query attention (GQA) [^gqa] use fewer K/V heads than Q heads. The fused op carries
`n_rep` (4 for 32 Q heads and 8 KV heads), and the kernel reads `kv_head = q_head / n_rep`, so Q heads share K/V rows without a
copy.

## The attention rewrite pass

Flash attention [^flash1] [^flash2] streams over K/V with a running (max, denominator, accumulator) triple in workgroup memory,
so the score matrix never exists. In poot it is a **compiler pass**, not an opt-in mode.

It runs in `compile` after canonicalization and RoPE recognition, and replaces each supported subgraph with one `Attention`
eqn. Unsupported patterns keep their primitives. Decode and prefill are the same op:

| Operand | Shape | Notes |
| --- | --- | --- |
| `q` | `[B, Hq, Lq, Dk]` | |
| `k` | `[B, Hkv, Lk, Dk]` | |
| `v` | `[B, Hkv, Lk, Dv]` | `Dv` is independent of `Dk`. |
| `mask` | `[B, Hm, Lq, Lk]` | Additive; `Hm` is 1 or `Hq` (ALiBi). |
| softcap | scalar | Optional. |

A sparse-attention indexer uses a block-selected form: no mask, the selected block ids and query positions instead. Each row
visits only the `(K + 1) * ratio` positions of its `K` selected blocks and its own unfinished block. The selection pass forms
`BlockTopK` and `SelectedAttention` eqns.

The planner turns the eqn into one generation request (shape, score transform, mask kind, key bound, schedule). One generator
serves every phase, target and head width. The lane count follows the device's workgroup memory; only a device that cannot hold
one lane's state gets the typed error `AttentionLds`.

## The streaming schedule

Decode, and any attention whose rows cannot share key blocks, takes the streaming schedule. One workgroup of `lanes`
threads runs per (batch row, query head, query row). Each lane strides over the keys with its own
running state. `lanes` is the widest power of two, at most 64, with `lanes * (dv + 2)` floats fitting workgroup memory.

The online softmax [^onlinesoftmax] keeps three accumulators per lane in LDS:

<FlashAttentionDiagram />

```rust
// Per lane, over its keys:
let score = softcap_or_identity(dot(q, k[t]) * scale) + mask[t];
let m_new = max(m, score);
let rescale = exp(m - m_new);
let weight = exp(score - m_new);
l = l * rescale + weight;
for d in 0..head_dim {
    o[d] = o[d] * rescale + weight * v[t][d];
}
m = m_new;
// Then one barrier; lanes merge partials weighted by exp(m_i - M).
```

- The accumulators live in LDS because private arrays with dynamic indices crash some SPIR-V drivers (RADV).
- A `-inf` score adds zero weight; a row with no visible key is `0 / 0`, as in the oracle.
- Peak memory is **O(head_dim)** per workgroup. The same kernel runs on wgpu, raw Vulkan, ROCm and PTX.

<details>
<summary>Bank-conflict swizzle</summary>

When `dv` is a multiple of the 32 workgroup-memory banks, each lane's partial `o` is stored with its channel XORed with
`lane % 32`. Every lane then uses a different bank, and the footprint stays `lanes * dv` words. A padded stride would also avoid
conflicts but can cost a resident workgroup per compute unit. The swizzle is in the shared generator, so all schedules use it.

</details>

## The tiled prefill schedule

A prefill has many query rows that read the same keys. The tiled schedule (FlashAttention-2 [^flash2]) lets them
share each key load:

- One workgroup serves a block of `br` query positions of one (batch row, key/value head). The `n_rep` query heads
  of the key/value head are packed into the block, so it has `br * n_rep` rows.
- The block's queries are staged in workgroup memory once. The keys are walked in blocks of `bc` (32 or 16); each
  block of keys, then of values, is staged once for every row. A two-byte cache (f16 or bf16) is widened to f32 as
  it is staged.
- Both products, `S = Q K^T` and `O += P V`, run as per-lane register tiles. The online softmax keeps one running
  maximum and sum per row; a block that every row sees whole is not masked.
- A causal block walks only the keys from its rows' earliest window start to its last row's position, and a live
  length bounds the walk. A key no row of the block sees is never read.

The planner chooses the tiling from the shape and the device:

| Rule | Value |
| --- | --- |
| Applies to | More than one query row, dense keys (single, split or paged), any mask but a block selection |
| Workgroup | The widest of 256, 128 and 64 lanes the device allows; 64 on RADV (Strix Halo), whose wider workgroups lose workgroup-memory writes |
| Registers | At most 64 accumulators per lane across the two tiles |
| Memory | The staged tiles fit the device's workgroup memory |
| Fill | At least one workgroup per compute unit; otherwise the streaming schedule |

Among the tilings that fit, the widest workgroup wins, then the most rows per block, then the wider key block. The
numerics are the same online softmax with a different summation order, so results match the oracle within the flash
tolerance, not bit for bit. Unlike the streaming schedule, a key that one row of a block sees is read by every row of
it: a non-finite key or value there reaches the rows that cannot see it.

## The block-selected schedule

The selected ids are per query row, so all `n_rep` heads of a key/value head read the same positions. Two schedules exist:

| Schedule | When | Shape |
| --- | --- | --- |
| **Grouped** | Rows keep the device full (at least two groups per compute unit). | One workgroup per (key/value head, query row), serving all `n_rep` heads. |
| **Ungrouped** | Decode, or a device whose workgroup memory cannot hold the `n_rep` head lanes. | One workgroup per head, one key per step. |

Grouped loads each selected key and value row once per group [^nsa]. Each step takes one block's keys (up to four), sharing one
load of `q` and one rescale. The request records the choice (`grouped`). Where a display watchdog bounds a dispatch, a long
chunk is cut into runs.

## Split keys, paged keys and the live length

| Form | Operands | Effect |
| --- | --- | --- |
| **Split keys** [^mla] | `k [B, Hkv, Lk, Dk - s]`, `k_shared [B, 1, Lk, s]` | Multi-head latent attention's `concat(k_nope, broadcast(k_pe))` is never built; the shared part is read once per key. |
| **Paged keys** | Pools `k [S, Hkv, Dk]`, `v [S, Hkv, Dv]`, `I32 read [B, Lk]` | Key `t` of row `b`, head `g` is pool row `read[b, t] * Hkv + g`; no gather or transpose. |
| **Live length** | `I32 len [B]` | Visits only the first `len[b]` keys, so a step costs the live length, not `cap`. |

**Paged keys** fuse only when the graph proves every word of `read` is a slot of the pool (the map's declared range, enforced at
bind). Other cached values (latent, indexer, sliding-window) keep the gathered view.

**Live length** keeps the grid and launch independent of `len`, so capture and replay stay valid. The graph builds
`len = pos + 1`, and `ops::attention_live` is the one definition:

- It requires `1 <= len[b] <= Lk` and bounds the length with an index guard whose witness is a validation output; an
  out-of-range length publishes nothing.
- It selects inactive key and value rows to zero before either matmul (a true select, so a NaN in an unused row cannot reach
  the output) and inactive scores to `-inf` before the softmax.
- The rewrite fuses it only when value ranges prove `1 <= len <= Lk`. A range from an index guard's clamp needs that guard's
  witness to be a declared validation output; a declared position slot needs none.
- Otherwise (score-mask-only graphs, partial guards, unprovable lengths) the capacity form or primitives stay, with unchanged
  results.
- The generated live kernel is F32 only. A BF16 or F16 chain stays primitives with selects at its own dtype: it runs on ROCm and
  PTX, and a SPIR-V target refuses the two-byte select with a typed `DtypeLowering`. Generated kernels clamp `len` into
  `0..=Lk`.

## Split-KV decode

Decode launches only `B * n_q_heads` workgroups, which leaves most of a large device idle. The split-KV schedule
(Flash-Decoding [^flashdecoding]) cuts the keys into `splits` chunks and runs two launches:

1. **Partials:** one workgroup per (row, split) runs the streaming body over its chunk and writes the unnormalized
   `(o[dv], m, l)` to scratch. A split past the live length, or fully masked, writes the neutral `(0, -inf, 0)`, so the scratch
   needs no initialization.
2. **Combine:** one workgroup per row merges the partials with the `exp(m_i - M)` weighting and writes the output.

The scratch is a plan-local buffer. The buffer plan shares one arena slot across layers, so the arena does not grow with layer
count. The split count is part of the request and the plan key. The planner chooses it as follows:

| Rule | Value |
| --- | --- |
| Applies to | Decode (`Lq == 1`) whose rows do not fill the compute units |
| Splits | At most 16, chunks of at least 128 keys |
| Falls back to streaming | Partial state over the single-buffer limit, or the 2-D fold passing the grid |

A scratch the device cannot allocate is refused with a typed `ScratchBytes`. The combine reassociates float sums, so results
match the oracle within a tolerance, not bit for bit.

## KV cache

Without a cache, K and V would be recomputed every decode step at O(L) cost. poot has two allocation schemes:

<KVCacheDiagram />

**Fixed capacity with causal masking.** K and V are `Storage::State` buffers of `cap` positions per layer. Each token writes at
`pos`; the kernel sweeps all `[cap]` positions under an in-graph mask. The grid is constant, so it is capturable as a CUDA
graph. Memory is `cap` whatever the sequence length.

**Paged KV** [^pagedattn]. Fixed-size blocks (16 tokens, `poot_llm::driver::block_table::BLOCK_SIZE`) come from a shared pool;
each layer has one `[pool_slots, kv_heads, head_dim]` pool. The driver keeps a block table per sequence and binds two inputs per
step:

| Input | Slot | Shape | Meaning |
| --- | --- | --- | --- |
| `read` | `Slot::SlotMap` | `[rows, cap]` i32 | Logical position to physical slot. |
| `write` | `Slot::WriteMap` | `[rows * tokens]` i32 | New token to pool slot, or -1 for padding. |

- A write map is bound only as a checked `ForwardSlotMap`, which refuses a slot outside the pool or named twice.
- The read map is declared in `[0, pool_slots)`, so a word outside the pool is a typed range error at bind.
- New rows go in with `ScatterUpdate` through `write`, in place on the donated pool, at a cost that follows the tokens.
- Attention reads the pools in place through `read` (a paged key). Blocks are allocated on demand and freed on completion.

### Storage dtype

The cache stores f16 by default, half the bytes of f32, as llama.cpp does. Attention computes in f32 whatever is stored.

| Dtype | Use |
| --- | --- |
| `f16` | The default. |
| `bf16` | Same size as f16, wider range, fewer mantissa bits. Not on wgpu or Vulkan: SPIR-V has no bf16 type, so the planner refuses it with a typed `DtypeLowering`. |
| `f32` | The exact reference, twice the bytes. |

The dtype a driver runs comes from, in order: an explicit option (`DriverOptions::kv_dtype`, `--kv-dtype` on the server and the
benchmark runner), the model's own preference (`ModelConfig::kv_dtype`), then f16. A family whose cache is read by contractions,
not only by attention (the DeepSeek and GLM-5.3-Flash latent and indexer caches), prefers f32: no contraction body reads a two-byte operand in
place yet, so a narrow cache there would be widened into an f32 copy every step.

- The write narrows: `DynamicUpdateSlice` and `ScatterUpdate` store an f32 update into a two-byte cache with round-to-nearest-even,
  one kernel, no narrowed copy of the new entries.
- The read widens: the tracer reads the cache through a `Cast` to f32, which the attention rewrite folds into the fused op, so
  the kernel loads two-byte keys and values and converts in registers.
- The oracle evaluates the same graph, so it holds the same rounded cache, and an exact-token gate against it compares like with
  like.

Measured against an f32 cache on qwen3-0.6b and qwen3-4b (bf16 and Q4_K_M checkpoints), teacher-forced over 737 positions of
mixed prose and code: f16 keeps the top token at 99.9 to 100 percent of positions (the one flip was a tie within 4e-4 nats),
with a mean top-token log-probability change of 4e-4 to 6e-4 and an identical 128-token greedy continuation. bf16 changes it
about seven to ten times more and also keeps the greedy continuation.

## Prefix caching

A request whose prefix matches earlier K/V blocks reuses them: the blocks are pinned, the block table points at them, and that
prefill is skipped. The match key is a hash of the token ids plus the effective model weights. The base model and each LoRA
adapter therefore keep separate entries, and a hot-reloaded adapter gets a fresh identity. This is allocation policy; the kernel
is unchanged.

## Implementation details

- **Widths.** The value width is independent of the key width, and a split key is a first-class operand layout. The matcher
  declines a chain whose key or value the typing rule cannot type, such as a single key head the matmul merely broadcasts.
- **Softcap.** Part of the score transform on every phase.
- **Head width.** No fixed limit: the lane count follows workgroup memory, so a 512-wide head runs everywhere with fewer lanes.
