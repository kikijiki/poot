# Architecture Overview

poot is a from-scratch LLM inference engine in Rust. It runs its own GPU kernels, lowered from ordinary Rust source, on wgpu (Vulkan/SPIR-V), raw Vulkan, ROCm (AMD, raw HSA) and PTX (NVIDIA), with no cuBLAS, cuDNN or other vendor math libraries.

Small-batch decode is dominated by host overhead: a naive loop issues hundreds of tiny dispatches per token. poot answers with two mechanisms:

- **Automatic fusion.** The IR is finer-grained than its kernels, so a compiler pass synthesizes one kernel per fusable region instead of choosing from hand-written fused kernels.
- **Capture and replay.** The decode graph has a constant shape (fixed-capacity KV plus masking), so its dispatch sequence is recorded once and replayed per token. PTX uses CUDA graphs, ROCm recorded AQL packets, raw Vulkan recorded command buffers, and wgpu a cached re-encode.

## The one pipeline

One path serves every model and backend.

<PipelineDiagram />

1. **Tracing.** A family's `Model::trace` is plain Rust over a `Builder`, once per step shape. See [Tracing a Model](./tracing.mdx) and [Models and the Registry](./registry.mdx).
2. **Optimization.** Transforms (CSE, RoPE fusion, the flash-attention rewrite, pointwise and reduction fusion, matmul tiling) rewrite the graph without changing its meaning. See [Fusion](./fusion.mdx).
3. **Planning.** `plan_eqn` gives each equation a plan: an imported or synthesized kernel, a view or alias, or a refusal. `compile` runs it last.
4. **Capture.** The executor allocates stable buffers and records the dispatch sequence once per model and KV capacity.
5. **Decode.** [The Driver](./driver.mdx) steps the executor. Per token the host writes the token id and position into slot buffers and replays or re-encodes; logits or the sampled id come back.

## Design principles

- **One pipeline.** Every model is traced, compiled, executed through one executor contract and driven by one generation loop. No family or backend gets a private route.
- **Primitive IR.** Attention, norms, RoPE and MoE routing are compositions. A new primitive needs a stated reason a composition cannot serve.
- **General optimization.** A rewrite fires on any graph with the right semantics, not on one tracer's spelling. Fusion is codegen from the graph, not a catalogue of fused kernels.
- **Capability is decided by planning.** A model runs on a backend if its graph compiles for that target; otherwise the planner returns a typed refusal naming the equation and the missing capability. There is no support list.
- **One semantic definition.** Each op is defined once, shared by tracing, the CPU oracle and every lowering.
- **Backend-neutral above the planner, family-neutral below the model.** A backend's limits are handled inside its lowering.
- **Adding a model is writing a graph.** A config type, a weight-name table, a fixture and a tracer over shared components, registered in the model registry. Nothing in the driver, planner, executors or server changes.
- **Types carry invariants.** Ownership, residency, dtype, layout, launch geometry and capability are types, not comments or string matches.
- **Verification proves behavior.** Device results match the CPU oracle within a stated tolerance, real checkpoints match an independent reference on tokens, and a skipped device test is reported as a skip.

## Current state

- **Backends.** Tracing, optimization, planning, kernel import, codegen and capture/replay work on wgpu, raw Vulkan, ROCm and PTX, for any family the registry holds.
- **Compile.** `compile` owns the pass sequence and returns a `Program` with plans, storage, slots and numerics. Runtime `DeviceCaps` and typed planner refusals are implemented.
- **Executor.** `Engine<D>` runs over a per-backend `Device`; the first step on an entry records, later steps replay.
- **Serving.** `poot-serve` serves every registered model through the driver on one engine thread. See [Serving design](./serving-design.mdx).
- **Weights.** Packed projections keep their stored representation through loading. Dense BF16/F16 weights stay as stored words with no host f32 copy, and packed MoE experts are read in place, so no expert table is materialized.
