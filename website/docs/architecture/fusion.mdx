# Fusion and Planning

Fusion takes the primitive graph and groups its eqns into a smaller set of kernel
dispatches. Planning assigns each group a concrete kernel specialization, either an
**imported kernel** (a `#[kernel]` Rust function) or a **synthesized kernel** (generated
on the fly from the op pattern). Together they reduce a decode step from one dispatch per
primitive eqn to a few dozen fused dispatches per token.

## Why this matters

Every dispatch costs host time, and every intermediate written to DRAM costs bandwidth. Fusion, a
standard ML-compiler technique [^xla] [^tvm] [^halide], removes both by keeping intermediates in
registers or shared memory. `poot_graph_ir::analysis::dispatch_count` gives a graph's static dispatch count:

| Stage                        | Effect on dispatches per token                                  |
| ---------------------------- | --------------------------------------------------------------- |
| Unfused primitives           | One per equation                                                |
| RoPE fusion                  | The rotate-half chain (about 6-8 dispatches) becomes one `Rope` |
| Pointwise + reduction fusion | Each fusable region becomes one dispatch                        |
| Flash attention rewrite      | Each attention layer's chain becomes one dispatch               |
| Capture and replay           | Native replay or cached wgpu dispatches reduce host work        |

## Imported vs synthesized kernels

**Imported kernels** are `#[kernel]` Rust functions compiled via pootc from source
(sources under `crates/pootc/kernels/<family>/`, with committed `.kir.json` assets under each consuming
crate's `assets/`). The plan carries the imported body and the executor dispatches its precompiled
SPIR-V/PTX/AMDGPU artifact. Imported kernels cover the shapes the synthesizer does not:

- Decode `MatMul` (M=1) and batched/bias GEMV variants (`gemv_coalesced*.rs`)
- `FlashAttentionDecode` / `FlashAttentionPrefill` when the region synthesizer does not apply
  (batched decode, or head dim above the LDS cap): `flash_decode.rs`, `flash_prefill.rs`
- `Gather`, `Scatter`, greedy argmax and the batched samplers (`gather_axis0.rs`, `scatter_axis0.rs`,
  `argmax_batched.rs`, `sample_*_gumbel_argmax_batched.rs`)

**Synthesized kernels** are generated by the fusion pass's codegen from the subgraph's
op pattern. A pointwise chain (`Mul -> Exp -> Add -> ...`) or a reduction-rooted region
(`Reduce(Max) -> Sub -> Exp -> Reduce(Sum) -> Div`) produces unique kernel IR on the fly.
The synthesizer writes the kernel IR; poot-codegen lowers it to LLVM IR and then to
SPIR-V/PTX/AMDGPU. Synthesized kernels handle the structural glue, normalization epilogues,
and elementwise chains. In the default pipeline they also cover prefill GEMMs (the tiled
GEMM), packed contractions, and flash attention (the region decode and prefill kernels), all
generated from the op's shape rather than selected from a menu. These are kernel choices the
planner records for an ordinary `MatMul` or `FlashAttention*` eqn, not separate ops.

## Fusable region shapes

**Pointwise chains.** `Binary` ops and the unaries `Neg`, `Exp`, `Log`, `Sqrt`, `Recip`, `Tanh`,
and `Erf` (plus the I32 bit ops and I32 `Select`) with compatible iteration spaces fuse into one
synthesized elementwise kernel. The activations are compositions over these, so SwiGLU and GeGLU
fuse as plain `Exp`/`Div`/`Mul` chains, and a value read more than once (the activation's input)
fuses as long as every read is inside the same region. `MatMul`, `Gather`, `Scatter`, `Concat`,
`Reduce`, the movement ops (`Reshape`, `Slice`, `Broadcast`, `Transpose`), and the unary `Round`
are fusion boundaries.

**Reduction-rooted regions.** A `Reduce` op followed by pointwise ops on the reduction
output fuses into one synthesized reduction kernel. The reduction kernel computes the
reduced value in shared memory, then the pointwise epilogue runs inside the same kernel.
Regions are last-axis, keepdim reductions. This is the shape of RMSNorm (sum-of-squares -> sqrt -> div) and softmax.

**Flash attention rewrite.** A separate rewrite inside `compile` pattern-matches
the exact chain the attention tracer emits. `matmul(q, k^T) -> scale -> mask -> reduce-max
-> sub -> exp -> reduce-sum -> div -> matmul(scores, v)`, and replaces it with a single
`FlashAttentionDecode` or `FlashAttentionPrefill` eqn. The planner then chooses its kernel:
a synthesized region kernel for decode (head dim at most 256) and for prefill (head dim at most
512, no softcap); a softcapped prefill takes the imported kernel. On wgpu the default
pipeline skips the prefill rewrite when
`Hq * L` exceeds 65535 workgroups. This rewrite fires once per attention layer [^flash1] [^flash2].

Canonicalization and matcher legality checks cover equivalent spellings and reject unsupported shapes.
The matchers recognize bounded patterns.

## Kernel specialization (planning)

`plan_eqn_analyzed` (in `poot-graph-plan`) assigns each eqn of the optimized graph a `Plan`: a compute
body, a compute body plus a `u32` metadata buffer, chunked dispatches, a
buffer alias or strided view, or a cross-rank collective. `compile` runs this planning as its last
step. The same `OpKind` can map to different bodies depending on shape and dtype. Kernel choice
is a plan property: the planner records, beside each plan, whether the body was generated from a
request, imported from a shipped kernel, or needs no dispatch at all.

| Specialization        | When                                             | Implementation                                                                                                            |
| --------------------- | ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------- |
| **Elementwise**       | `Fused` pointwise region                         | Synthesized: one thread per element                                                                                       |
| **Reduction**         | `FusedRow` region                                | Synthesized: block reduce + epilogue in shared memory                                                                     |
| **GEMV**              | `MatMul` with M=1 (decode)                       | Imported or `kernelgen::gemv_lds`: one workgroup per output row                                                           |
| **Tiled GEMM**        | `MatMul` with f32 operands, M>1 and a 2-D weight | Synthesized by `kg::tiled_region`: 2-D tile with LDS staging (not under `FusionPolicy::MoeHangGuard`)                     |
| **Tensor-core GEMM**  | bf16 operands                                    | WMMA bodies on PTX and ROCm; not on wgpu                                                                                  |
| **Flash decode**      | `FlashAttentionDecode`                           | Synthesized `kg::flash_region_decode` (head dim at most 256); one workgroup per (batch row, Q head)                       |
| **Flash prefill**     | `FlashAttentionPrefill`                          | Synthesized `kg::flash_region_prefill`, or imported `flash_prefill.rs` for a softcap; one workgroup per (head, query row) |
| **Dequant GEMV/GEMM** | `PackedContraction`                              | Generated decode from the format descriptor, then contraction                                                             |

## Plan::ComputeMeta

An imported, shape-generic kernel reads its dimensions from a small read-only `u32` buffer
instead of baked-in constants. `Plan::ComputeMeta { body, key, meta }` carries that buffer,
bound between the eqn's data inputs and its output. This lets one compiled binary serve
multiple configurations. For flash decode the buffer is
`[Hq, D, cap, n_rep, scale_bits, B, mask_head_stride, mask_batch_stride]`; `scale` rides as raw
`f32` bits because it is not always `1/sqrt(D)`.

## The compile pipeline

`poot_graph_plan::compile(graph, target, options)` runs the graph passes and planning together and
returns a `Program`. `Target` combines the backend with runtime-measured `DeviceCaps`.

The current order is canonicalization, CSE, iota folding, RoPE and attention recognition, DCE, packed
contraction/row-gather recognition and the packed escape check, legalization, dense BF16 recognition,
reduction/dtype preparation, then fusion, tiling and flash-region synthesis. Planning then runs over
the optimized graph to produce the equation plans, storage decisions and slot schema. `Program::passes()`
lists transformations that changed the graph.

Canonicalization preserves the primitive computation's rounding and arithmetic order. General scalar
factoring across a contraction and replacing reciprocal multiplication with division are declined
without an exact proof. `Program::numerical_declines()` reports the original candidate value and a
typed reason; the graph remains compilable through its original operations. F32 multiplication by
one on a contraction operand is a proved identity that canonicalization can remove.

Attention with an already-scaled query can still select a flash region: the scaled query remains a
region input, and the region's post-contraction scale is one. Reciprocal softmax keeps its original
operations because the current flash representation uses division. Explicit F16/BF16 casts remain
fusion boundaries. A narrow contraction result rounds before a following F32 epilogue, even when
that epilogue is fused. The numerical comparison class describes device scheduling; it does not
prove a semantic graph rewrite legal.

`FusionPolicy::MoeHangGuard` disables the attention/fusion/tiling group for the existing guarded
execution paths; it does not bypass packed recognition or legalization. Callers select typed options,
not their own pass sequence.

Planner refusals are typed and name the equation and missing capability. The executor contract
consumes the complete `Program`: `compile_staged` stages it for one device and `Executor::add_entry`
loads it, so no caller re-plans the graph.

## What fusion reports

`poot_graph_ir::analysis::dispatch_count` and `poot_graph_ir::analysis::peak_transient_bytes` (peak live
activation bytes) are computed from the graph. `poot-serve` runs no generation engine, so its generation counters stay at
zero.

## Implementation details

- **Flash is a structural rewrite.** Pointwise/reduction fusion synthesizes
  kernels; flash attention is a separate matcher that replaces a recognized attention subgraph with
  one `FlashAttention*` eqn. Gates that refuse the rewrite (unequal head widths, softcap on decode,
  batched prefill) keep the safe primitive graph, see [Attention](./attention#implementation-details).
- **Specialization vs source.** A `Plan` body is either an imported `#[kernel]` (loaded from the
  committed `pootc` assets) or a synthesized body from `poot-kernelgen`. Both lower through
  `poot-codegen`; the planner decides which path, not the model tracer.
