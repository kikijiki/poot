# Fusion and Planning

Fusion groups the primitive graph's eqns into a smaller set of kernel dispatches. Planning then assigns each group a concrete
kernel: an **imported kernel** (a `#[kernel]` Rust function) or a **synthesized kernel** (generated from the op pattern).
Together they reduce a decode step from one dispatch per primitive eqn to a few dozen fused dispatches per token.

## Why this matters

Every dispatch costs host time, and every intermediate written to DRAM costs bandwidth. Fusion [^xla] [^tvm] [^halide] removes
both by keeping intermediates in registers or shared memory. `poot_graph_ir::analysis::dispatch_count` gives a graph's static
dispatch count.

| Stage | Effect on dispatches per token |
| --- | --- |
| Unfused primitives | One per equation. |
| RoPE fusion | The rotate-half chain (about 6-8 dispatches) becomes one `Rope`. |
| Pointwise + reduction fusion | Each fusable region becomes one dispatch. |
| Contraction epilogue | A bias, activation or residual add rides in its contraction. |
| Widening-cast folding | A bf16 norm scale or bias is widened inside the fused region that reads it; its cast is not a dispatch. |
| Computed-constant CSE | Tables built from one recipe (such as the RoPE tables every layer asks for) exist once and are gathered once per step. |
| Flash attention rewrite | Each attention layer's chain becomes one dispatch. |
| Capture and replay | Native replay (CUDA graphs, HSA packets, Vulkan command buffers) or cached wgpu dispatches reduce host work. |

## Imported vs synthesized kernels

**Imported kernels** are `#[kernel]` Rust functions compiled by pootc (sources in `crates/pootc/kernels/<family>/`, committed
`.kir.json` assets under each consuming crate's `assets/`). The executor dispatches their precompiled SPIR-V/PTX/AMDGPU
artifact. They cover only what the synthesizer does not:

- Greedy argmax in two stages, the uniform generator and the batched samplers.
- Packed row gathers and the packed bf16 to f32 conversion.
- The state-copy kernel for a device without a native buffer copy.

**Synthesized kernels** are generated from the subgraph's op pattern: the synthesizer writes kernel IR, and `poot-codegen`
lowers it to LLVM IR and then SPIR-V/PTX/AMDGPU. They cover every contraction (decode GEMV, tiled GEMMs, packed contractions),
every unary, binary and scalar-literal op, attention (one generator for decode and prefill), normalization epilogues and
elementwise chains. Data movement (`Gather`, `Slice`, `Concat`, `Transpose`, `Broadcast`, `DynamicUpdateSlice`) is one
generated kernel for every op and storage, copying bits without decoding. These are choices the planner records for ordinary
`MatMul` or `Attention` eqns, not separate ops.

## Fusable region shapes

### Pointwise chains

`Binary` ops, the unaries `Neg`, `Exp`, `Log`, `Sqrt`, `Recip`, `Tanh`, `Erf`, the I32 bit ops and `Select` fuse into one
synthesized elementwise kernel when their iteration spaces are compatible.

- SwiGLU and GeGLU fuse as plain `Exp`/`Div`/`Mul` chains; a value read more than once fuses if every read is in the region.
- `MatMul`, `Gather`, `Concat`, `Reduce` and the movement ops (`Reshape`, `Slice`, `Broadcast`, `Transpose`) end a pointwise
  region. A contraction absorbs the chain after it instead.
- A float `Select` is a hardware bit select, so a NaN or Inf in the unpicked branch never reaches the result. It joins
  pointwise regions only, not row regions.
- Over BF16 or F16 it plans as its own kernel on ROCm and PTX; SPIR-V refuses it with a typed `DtypeLowering`.

### Contraction epilogues

A dense contraction (a `MatMul`, a weight kept in checkpoint `[N, K]` order, or the routed `IndexedMatMul`) whose result feeds
only pointwise steps becomes one `ContractionEpilogue`: bias, activation or residual add run in registers before the single
store. Other values the chain reads are read at their broadcast position. A BF16 or F16 head rounds to its dtype before each
step, so the fused kernel computes what the unfused kernels would have stored.

| Head | Fuses | Stays separate |
| --- | --- | --- |
| Dense contraction | At every row count (decode Gemv at one row, tiled GEMM above) | |
| `MatMul` | Generated tiled GEMM (f32 `[K, N]` weight above one row) or one-thread-per-output body | Decode GEMV, batched-weight tiled schedules |
| Routed expert matmul | Gate weighting, on both decode Gemv and register-tiled schedules | |

### Reduction-rooted regions

A last-axis, keepdim `Reduce` followed by pointwise ops on its output becomes one kernel: the reduction runs in shared memory,
then the epilogue. This is the shape of RMSNorm and softmax.

### Flash attention rewrite

A rewrite in `compile` matches the chain the attention tracer emits and replaces it with one `Attention` eqn for decode and
prefill, once per layer [^flash1] [^flash2]:

1. `matmul(q, k^T)`, scale, mask.
2. Softmax: reduce-max, sub, exp, reduce-sum, div.
3. `matmul(scores, v)`.

The planner generates one online-softmax kernel for every head width. A launch the target cannot make even on a 2-D grid is
refused and the decomposition stays. Matchers recognize bounded patterns and reject unsupported shapes.

## Kernel specialization (planning)

`plan_eqn` (in `poot-graph-plan`) assigns each eqn of the optimized graph a `Plan`. It is one of:

- a compute body;
- a compute body plus a `u32` metadata buffer;
- chunked dispatches;
- a buffer alias or strided view;
- a cross-rank collective.

`compile` runs this planning as its last step. The same `OpKind` can map to different bodies depending on shape and dtype.
Kernel choice is a plan property: beside each plan, the planner records whether the body was generated from a request, imported
from a shipped kernel, or needs no dispatch at all.

| Specialization | When | Implementation |
| --- | --- | --- |
| **Elementwise** | `Fused` pointwise region | Synthesized: one thread per element. |
| **Reduction** | `FusedRow` region | Synthesized: block reduce + epilogue in shared memory. |
| **GEMV** | `MatMul` with M=1 (decode) | Synthesized: `kernelgen::gemv_lds`, one workgroup per output row. |
| **Tiled GEMM** | A dense contraction with M>1: a `MatMul` with f32 operands and a shared or per-batch weight, or a weight in checkpoint `[N, K]` order | Synthesized register-tiled GEMM: LDS-staged tiles, a register tile per lane, the tile sized from the shape and the device. |
| **Attention** | `Attention` | Generated from `KernelRequest::Attention` (`AttentionSpec`): one workgroup per (batch row, Q head, query row), lanes striding the keys, softcap optional. A block-selected prefill serves the `n_rep` heads of a key/value head in one workgroup. |
| **Dequant GEMV/GEMM** | `PackedContraction` | Generated decode from the format descriptor, then contraction. |

## Launch metadata

An imported, shape-generic kernel reads its dimensions from a small read-only `u32` buffer instead of baked-in constants. A
dispatch's `launch.meta` carries that buffer, bound between the eqn's data inputs and its output. One compiled binary then
serves multiple configurations. The sampling kernels read their vocabulary and chunk sizes from it.

## The compile pipeline

`poot_graph_plan::compile(graph, target, options)` runs the passes and planning and returns a `Program`. A GPU `Target` pairs a
backend with measured `DeviceCaps`; an AIE `Target` carries `AieCaps`. Every target runs every pass on every graph (no
per-graph skip), and callers choose typed options, not pass sequences. The order:

1. Canonicalization, CSE, iota folding.
2. RoPE and attention recognition, DCE.
3. Packed contraction and row-gather recognition, packed escape check.
4. Legalization, dense BF16 recognition, reduction and dtype preparation.
5. Fusion, tiling and flash-region synthesis.

Planning then produces equation plans, storage decisions and the slot schema. `Program::passes()` lists the passes that changed
the graph.

### Numerics and declines

Canonicalization preserves rounding and arithmetic order. Scalar factoring across a contraction and replacing reciprocal
multiplication with division are declined without an exact proof; F32 multiplication by one is a proved identity it may remove.

- `Program::numerical_declines()` gives the candidate value and a typed reason.
- `Program::declines()` lists attention and RoPE chains the matchers left alone, naming the first failed check.
- An already-scaled query can still fuse (the region's scale is one). Reciprocal softmax does not, since flash uses division.
- F16/BF16 casts stay fusion boundaries, and a narrow contraction result rounds before a following F32 epilogue.

### Packed expert legalization

A packed expert stack splits into expert ranges when a source passes the single-buffer limit or a bit offset passes the index
width:

| Backend | Index width | Splits |
| --- | --- | --- |
| PTX, ROCm | 64 bits | Only at the buffer limit |
| Raw Vulkan, wgpu | 32 bits | Where a source passes 2^32 bits (512 MiB) |

An expert whose slab alone passes the bound is refused as a dispatch size overflow, never wrapped. Planner refusals are typed
and name the equation and capability. `compile_staged` stages the `Program` for one device and `Executor::add_entry` loads it.

## What fusion reports

`poot_graph_ir::analysis::dispatch_count` and `poot_graph_ir::analysis::peak_transient_bytes` (peak live activation bytes) are
computed from the graph. `poot-serve` reports the driver's compile count and device bytes on `/metrics`.

## Implementation details

- **Flash is a structural rewrite.** Pointwise and reduction fusion synthesize kernels. Flash attention is a separate matcher
  that replaces a recognized attention subgraph with one `Attention` eqn. Gates that refuse the rewrite keep the safe primitive
  graph (a live length no validation bounds; a key or value the op's typing rule cannot type, such as a single key head the
  matmul merely broadcasts). See [Attention](./attention#implementation-details).
- **Specialization vs source.** A `Plan` body is either an imported `#[kernel]` (loaded from the committed `pootc` assets) or
  a synthesized body from `poot-kernelgen`. Both lower through `poot-codegen`. The planner decides which path, not the model
  tracer.
