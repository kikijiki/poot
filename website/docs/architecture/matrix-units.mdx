# Matrix Units and the Cost Model

A contraction can run on the vector units, as a register-tiled body or a Gemv, or on the matrix units of the GPU. This page
states what a device reports, which schedules use it, how the planner chooses between schedules, and how a device's compiler
can correct that choice.

## What a device reports

Each runtime reports the matrix-multiply **fragments** its device exposes as `MatrixUnits`, one config per operand dtype. A
fragment multiplies two operands of one narrow dtype and accumulates in f32. Only the 16x16x16 shape is lowered, in `bf16` or `f16`.

| Backend | Source | Dtypes |
| --- | --- | --- |
| ROCm | RDNA3 and 3.5 (gfx11) WMMA, 32-lane waves | bf16, f16 |
| PTX | `wmma` on compute capability 8.0 and newer | bf16, f16 |
| Raw Vulkan, wgpu | `VK_KHR_cooperative_matrix` configurations the driver reports | f16 |

A code that is not recognized (gfx12, CDNA, older NVIDIA) has no matrix unit rather than a guessed one, and its programs run the
exact schedules. The planner reads only this description, never a device name. Each config also carries the unit's rate against
the vector units; a capability whose rate nobody sourced is `Unknown`, and the cost model gives that unit no speed credit.

## Fragment contraction

The register-tiled contraction has a fragment variant: each wave holds fragments of the output tile and loops over K with a
pipelined, software-staged read. A routed expert contraction reaches it through block-aligned grouping, so every tile holds one
expert's rows. Whether a contraction takes it is the outcome of [the selection](#one-selection-per-contraction), not a separate
question; see [Operand precision](./graph-ir.mdx#operand-precision). A narrowed activation is rounded once, by the op that produces
it, and stored narrow.

## Fragment attention

The [tiled prefill schedule](./attention.mdx#the-tiled-prefill-schedule) has a fragment body too. Both products, `S = Q K^T`
and `O += P V`, run on fragments, with the query held in registers and the running softmax maximum kept per row in one lane.
The planner chooses among every feasible micro-tile for the shape and device. An f16 attention runs only over an f16 cache.

## The contraction cost model

Every choice among contraction schedules uses one model, `ContractionCost`. It prices a schedule in FMA issues:

- the multiply-accumulates of the tile, divided by the unit's rate for a fragment;
- one lane's LDS reads;
- each staged value: a global load, its LDS write and its share of the barriers of a round;
- for a Gemv, each value a lane reads straight from global memory;
- the rounding of a staged narrowed operand.

## One selection per contraction

The planner makes one choice for each contraction, dense or packed, grouped by expert or not: the cheapest candidate under the cost
model. The candidates are

- the exact register tilings;
- the exact Gemv, where the contraction has one;
- the fragment tilings of the dtype the precision policy permits, where the device has a matrix unit for it.

A grouped contraction is priced at the block of rows its grouping will use, chosen together with the tiling, so the empty rows of a short expert tile are in every cost.
A tie goes to an exact schedule: a narrowing rounds, so it must win. No fixed row count switches between the Gemv and the tiled schedule, and the criterion never
mentions a model, a shape or a benchmark.

The precision is the selection's output. `narrow` and `split` permit narrowing and `exact` forbids it, but a contraction reads its operands
narrowed only when a fragment tiling is the cheapest candidate. The precision pass and the final plan ask the same question of the same shape, so they cannot disagree.

## Register budget

A lane holds the accumulators of its tile and, in a pipelined loop, the operand reads staged for a round. The budget comes from
the register file the runtime reports: a quarter of a lane's registers hold accumulators, and the loop as a whole may hold half. A tiling over
either bound is not offered, so a tile that would spill is replaced by a shallower one. Where the runtime reports no register
file, the planner uses a portable figure and the plan records that it did. This is the register model: a count the planner makes
without running a compiler.

## Compile feedback

Whether a kernel spills is the compiler's to say. A device whose compiler can be asked (PTX today) gives the planner that answer.
The planner then compiles a candidate's probe, the kernel body the generator emits for the contraction's shape and tiling without
its epilogue, and takes the cheapest candidate that does not spill:

- Candidates are compiled in cost order, so the first compile is usually the kernel the plan runs. The register model only prunes
  a tiling that cannot fit the lane's whole register file, and each fragment geometry is weighed at every whole-request depth.
- A kernel spills when the compiler gives it any per-lane local memory. A probe the compiler refuses is a tiling the device does not run.
- If no candidate of a contraction holds, planning refuses the contraction by name instead of falling back to a tiling that may spill.
- A verdict is a function of the probe and the compiler. Verdicts are cached on disk by the compiler's identity (the driver release
  and compute capability on PTX) and the probe's digest, so a restart reads them back and another driver starts afresh.
- The plan names the compiler whose verdicts chose its tilings, and plans made with different compilers are different plans.

The division of labour follows the architecture: the device is mechanism and reports the registers and local memory of a kernel it
was handed; the engine owns lowering, compiles each probe through its own kernel cache and passes the verdicts to the planner. The
driver attaches the device's feedback at the one place it compiles, so every program the driver compiles plans with it and a caller
cannot leave it out. The probe has no epilogue, so a contraction whose fused epilogue raises its register pressure
past the file could still spill.

Tools that plan without a GPU (the plan summary and the launch census) plan without feedback on purpose, stay
GPU-free and describe the register model's plan, which can differ from the plan a device with feedback runs. wgpu, raw Vulkan and ROCm report
no compiler registers today and plan with the register model alone.

## Calibration

The ratios of the cost model are memory-hierarchy figures that only a measurement on the device gives. They are kept per device
identity, together with the Gemv geometry (columns per workgroup, lane run and width). A device nobody measured is never given a
neighbour's figures: it plans with one named portable entry, and the plan records that it was uncalibrated. The figures only rank
schedules that are all correct, so a wrong ratio costs speed and never correctness.

`scripts/calibrate-launch` fits them. It times every candidate tiling pinned through a compile option and writes an entry for
review; modes cover the dense tilings, the indexed Gemv against the grouped tiling, packed expert stacks and the Gemv columns.

## Weight format

A driver holds its weights in one format. Under `narrow` on a target whose matrix units take f16, a bf16 weight read only by
dense contractions and embedding gathers is stored as f16, and a tied embedding and head share one copy. A weight f16
cannot hold is refused when it is bound. See [Operand precision](./graph-ir.mdx#operand-precision).

## Seeing what was planned

The launch census is a committed record of every contraction and attention schedule the planner picks for the reference models
at their real dimensions, on each reference target. A change to a figure the planner reads changes a row, so a review sees the
schedules that moved. See [Test](../develop/test.md#launch-census).
