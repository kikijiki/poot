# The Graph IR

The graph IR is poot's central abstraction: a flat, typed, topologically ordered list of primitive tensor equations in SSA form. The tracer, the fusion pass, the backends and the executor all produce or consume it.

## Why a fine-grained primitive IR

General kernel fusion needs an IR finer-grained than the kernels it produces, as in XLA [^xla], TVM [^tvm] and JAX [^jax]. Attention, RMSNorm, RoPE and SwiGLU are therefore compositions of matmul, reduce, elementwise and broadcast, not opcodes.

Flash attention [^flash1] is not a primitive either. A model composes attention with `ops::attention_masked(...)`, and `compile` rewrites supported subgraphs to one fused dispatch, depending on shape, target and fusion policy.

## Graph structure

A `Graph` is private; it is read through accessors and changed only through a checked edit. Its main tables:

- `values`: shape, dtype and storage class per id.
- `inputs`: all binders. `consts` and `slots` are subsets.
- `eqns`: topologically ordered SSA equations. Each has an `op`, `inputs` (a `ValueId` or a literal) and one `out`.
- `outputs`: the result, witnesses, exports and next-state values (`OutputKind`).

`Builder::finish` and `GraphEdit::commit` check the whole graph. A pass opens `graph.edit()`, changes the draft and commits it; a rewrite that loses a witness, an export or a carried-state pair, or changes the result's type, is refused with a typed error.

`ValueId` is a `u32` newtype. A value is defined by the one `Eqn` whose `out` is its id, so there are no separate def-use chains.

## Storage classes

| Class        | What it is                                                                                                   |
| ------------ | ------------------------------------------------------------------------------------------------------------ |
| `Device`     | An ordinary intermediate tensor: attention scores, MLP outputs, the residual stream                          |
| `Const`      | A weight or table, identified by its `WeightRef`, never by a name; weight caches never reuse different bytes |
| `Slot(Slot)` | A per-step input in a stable device buffer the host rewrites in place                                        |
| `State`      | A buffer carried across decode steps: the KV cache                                                           |
| `Computed`   | A compiler-defined constant, such as a folded `Iota`                                                         |

**Slots.** `Token` and `Pos` carry the step's ids and absolute positions. `SlotMap` and `WriteMap` carry paged KV reads and writes, each declaring the range of the words it holds, which the bind checks. Other roles (the adapter index, the expert pool, the sampler inputs) are defined by the pass or feature that declares them. The attention mask is not a slot: it is computed in-graph from `Pos`.

**State.** A state buffer is pre-allocated to `cap` per layer. `Graph::state()` pairs each `state_in` with a `state_out` of the same type. The executor overwrites the buffer with `state_out` (the JAX `donate_argnums` contract), which also orders the KV read before the KV write.

## Primitive operations

Tracers emit the primitives: elementwise, reduce, movement, matmul, gather/scatter and quantization. The optimizer introduces the composites (`Fused`, `FusedRow`, `ContractionEpilogue`, `Attention`, `Rope`, `BlockTopK`, `SelectedAttention`, the packed and dense contraction ops). Each has the semantics of the chain it replaces, and a tracer cannot emit them.

`Scan` is the exception. It states a recurrence, and tracers emit it with a primitive definition the CPU oracle evaluates.

A sparse-attention indexer writes its selection as primitive chains. The selection pass of `compile` forms `BlockTopK` and `SelectedAttention` from them, and a device that cannot plan them refuses the composite.

No op records a kernel choice; which kernel runs an eqn is a property of its plan.

## What composites decompose to

The tracer records a higher-level op as primitives. RMSNorm [^rmsnorm] is seven eqns, fused into one reduction kernel:

```text
sq  = Mul(x, x)
ss  = Reduce(Sum, sq, axis=-1, keepdim)
ms  = Mul(ss, 1/D)
mse = Add(ms, eps)
den = Unary(Sqrt, mse)
xn  = Div(x, den)
out = Mul(xn, weight)
```

RoPE [^rope] is the rotate-half chain (`ops::rope_partial`), with `cos` and `sin` gathered from constant tables:

```text
x1, x2 = Slice(x, 0..D/2), Slice(x, D/2..D)
out = Concat([Sub(Mul(x1,cos), Mul(x2,sin)),
              Add(Mul(x1,sin), Mul(x2,cos))], axis=-1)
```

`compile` replaces it with one `Rope { rot }` eqn over `[x, cos, sin]`, one synthesized kernel instead of about 6-8 dispatches.

Softmax is the two-pass safe pattern: a Max reduce, subtract, exp, a Sum reduce, divide. Flash attention uses the streaming "online" variant instead; see [Attention](./attention#the-streaming-schedule).

## Host-side shape inference

Every `OpKind` implements `infer(input_types) -> output_type`, run on the host at trace time. All shapes are static, so:

- the executor knows every buffer size before the first dispatch and allocates at stable addresses, which recorded replay (CUDA graphs, HSA packets, Vulkan command buffers) requires;
- the planner picks kernel specializations (GEMV vs GEMM, the attention schedule) at compile time.

Per-step inputs (`Slot::Token`, `Slot::Pos`) are small buffers the host writes each token. Output shapes never depend on slot values, because the KV capacity is fixed, so a captured graph stays valid at every position.

## Operand precision

Every op that multiplies two float operands (`MatMul`, the dense, grouped, packed and indexed contractions, and attention) carries an `OperandPrecision`:

- `Exact`: the operands enter the products as the graph declares them.
- `Narrow(bf16 | f16)`: each operand not already of that dtype is rounded to it (nearest even; an f32 beyond f16's range becomes infinity, never a clamp) before the products, which accumulate in f32. Attention rounds Q, K, V and the probabilities where they enter `P V`.
- `Split(bf16 | f16)`: an f32 operand enters as a high and a low part of that dtype, so the product is near f32 accuracy.

The precision is part of the op, so the CPU oracle evaluates exactly what a device must compute. A narrowed or split op runs on a matrix unit only: the planner has no GEMV, scalar-tile or streaming-attention schedule that rounds its operands, because rounding there costs accuracy and buys no speed. The published numerics class follows the ops: a program with a narrow op compares with the narrow-storage tolerance, a split one with the reassociating tolerance.

One driver-wide policy, `--matmul-precision exact|split|narrow`, is a permission, not an obligation. The `select_operand_precision` pass reads that policy, the target's matrix units, the operands' dtypes and one answer from the planner: is a fragment tiling the cheapest schedule for this op? That is the planner's one selection per contraction: an argmin of one cost model, rounding included, over the exact scalar tilings, the exact GEMV and the fragment tilings of the permitted dtype, a tie going to an exact schedule. The final plan makes the same selection on the same shape, so the precision is its output and the two cannot disagree. See [Matrix units](./matrix-units.mdx#one-selection-per-contraction).

- Where a matrix unit wins, a contraction or attention takes f16 on a target with f16 fragments and bf16 otherwise.
- Where it does not, the op stays `exact`: a decode row is a GEMV, a one-wave workgroup (wgpu) costs more than the exact tiles, and a target with no matrix unit has none.
- The criterion is a property of the schedule, the device and the cost model, never of a shape, a model or a benchmark.
- The planner holds to the decision: an op that declares a narrowed precision and has no matrix-unit schedule is refused by name, never run exactly in silence.

The default is `narrow`; `exact` stays selectable and is the reproducible policy. Because the decision follows the schedule, the rounding a token sees depends on the batch it is run in: a decode step is exact, a prefill chunk large enough for a matrix unit is narrowed, so greedy outputs can differ with batch occupancy and chunking. `exact` does not.

No operand is range-scaled. A value beyond f16's range (65504) rounds to infinity.

- The infinity reaches the logits as a non-finite value.
- Serving refuses that step with a typed error instead of sampling a token.
- `exact` avoids the rounding.
- Every checkpoint measured stays inside the range.

One case stays finite. A model that softcaps its attention scores (Gemma 2) maps an infinite score to the cap, so an overflowed attention query there gives a wrong but finite row. That is a known limit of the default, and the one the range detector covers.

`--check-ranges` is a compile option, off by default.

- Every operand an f16-narrowed op rounds gets a validation witness, on the same channel the router checks use.
- A step that leaves the range fails with a typed validation error.
- The error names the first operation, its layer and the operand, softcap or not.
- Off, no witness and no extra operation exist: the program is the one compiled without the option.

The generated kernels round to f16 and widen from it with the device's own conversion instructions on ROCm and NVIDIA. On Vulkan they round with integer arithmetic on the f32 bits, because the driver may drop a convert-and-convert-back pair. Both forms give the same bits for every f32 value.

The driver also stores its weights in one format. Under `narrow` on a target whose matrix units take f16, a bf16 weight that only dense contractions and embedding gathers read is declared f16 in the graph (the `store_weights_f16` pass). It is rounded to f16 once, when it is bound, so the kernels read it as stored and the oracle evaluates the same values.

The decision reads three things and nothing else:

- the policy;
- the target's matrix units;
- the kinds of a weight's readers, never a shape or the precision a reader plans.

Three consequences follow:

- Every program of a driver (prefill, decode) holds a weight in the same format.
- A tied embedding and head share one stored tensor, so they upload one copy.
- Any other bf16 weight (a norm scale, a router) keeps the checkpoint's format.

A weight that f16 cannot hold (beyond 65504, an infinity or a NaN) is refused at bind with a typed error naming the weight and the element.

### Measured agreement of narrow with exact

A checkpoint is compiled twice on one device and one weight upload, once `exact` and once `narrow`. Both programs score the same 640 tokens (five windows of 128, teacher-forced, logits at every position) and their next-token distributions are compared position by position. This is the `llama-perplexity --kl-divergence` method with the exact program as the reference.

- **top-1** is the fraction of positions where both programs rank the same token first.
- **mean KL** is the mean of KL(exact || narrow) in nats.
- **max shift** is the largest `|logit narrow - logit exact|` over every logit of the text.

A row passes when:

- the mean KL is at most 1e-3;
- the max shift is within the ceiling recorded for that row: the measured shift times 2.4 (the largest spread of one checkpoint's shift across the three f16 backends), rounded up;
- every token flip is a near tie: the exact program's two candidates were within twice that ceiling of each other. This is the tie rule of the tier-3 contract, and the ceiling enforces it, because logits that move by at most the ceiling cannot flip a wider gap.

The top-1 fraction is reported, not gated. For scale, llama.cpp's own CPU and Vulkan backends differ by about 1.4e-3 in mean KL on a similar text. The AMD rows are from the Strix Halo box (gfx1151); the NVIDIA PTX rows are from rented RTX 4090 and A40 GPUs, which gave identical numbers.

What the table says:

- **Contractions use f16 wherever the target has f16 fragments (ROCm, NVIDIA, wgpu and raw Vulkan on RADV).** f16 is more accurate than bf16: 18 to 40 times lower mean KL on ROCm, which has both. Its activations are not scaled: an activation beyond f16's range becomes infinity and the step is refused. On ROCm, against bf16, f16 costs 3% of prefill time to first token and 2% of decode time per token on Qwen3 4B, and is faster on Qwen2.5 1.5B Q4_K_M (24% less to first token, 10% less per token). The ROCm bf16 rows are a measured comparison on the same device with its units cut down to bf16, where attention over the f16 KV cache stays exact. bf16 is the dtype where the target has bf16 fragments alone.
- **Gemma 3 is the sensitive family.** It has the largest logit shift under every dtype (0.4 to 7.9), and under bf16 a few positions move far: KL 0.02 at one position on ROCm and 0.33 on NVIDIA.
- **Gemma 3 under bf16 on NVIDIA misses the mean-KL ceiling (1.9e-3).** The two exact programs agree across AMD and NVIDIA to within 0.005 (every 512th logit of every position compared), so the gap is the bf16 rounding itself: at the same sensitive positions, a different but correct accumulation order moves a bf16 result further. The NVIDIA rows above were measured when NVIDIA narrowed to bf16. It now narrows to f16 like the other targets, and its f16 rows have not been measured yet. `exact` is unaffected.
- **The default is `narrow`.** Every row above passes its gate on every backend, so the engine compiles `narrow` unless `--matmul-precision exact` says otherwise.

## Quantization

`PackedDequant` is the one packed-weight primitive. Its `poot-quant::PackedWeight` descriptor names the `WeightFormat`, shape and source roles. The compiler recognizes dense projections as `PackedContraction` and embedding lookups as `PackedRowGather`, and generated kernels decode only the weight values they consume.

GPTQ, AWQ, supported GGUF quants and the registered FP8/E2M1 layouts use this lowering. A packed MoE expert stack is rewritten when its weights are bound into one indexed packed contraction that decodes only the selected experts' blocks.
