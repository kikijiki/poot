# Serving design

`poot-serve` is an OpenAI-compatible HTTP server. It parses and bounds requests, loads any registered model as a `ModelHandle`, and serves completions and chat from one scheduling loop over the driver's `step`. Embeddings, rerank and LoRA administration run on the same engine thread, between requests. Operator guides live under [Serving](../serve/index.md).

## API

| Endpoint | Description |
| --- | --- |
| `POST /v1/chat/completions` | Chat completion, streaming (SSE) or buffered JSON |
| `POST /v1/completions` | Raw text completion |
| `POST /v1/embeddings`, `POST /v1/rerank` | Vectors and scores (an encoder, or a decoder's embedding pass) |
| `GET /v1/models`, `GET /v1/models/{id}` | The served model(s) |
| `/v1/lora_adapters` | LoRA administration: list, hot-load, unload |
| `GET /metrics`, `GET /metrics/prometheus` | Server metrics as JSON, or in Prometheus format |
| `GET /health` | Liveness probe |

## The scheduling loop

**Continuous batching** [^orca] [^vllm]. In-flight requests share one batch per token. When one finishes, a waiting request takes its slot before the next step, so the batch never drains.

<ContinuousBatchingDiagram />

Graph shapes are static, so prepared entries are sized to the engine's row capacity and every step runs at that width, with empty rows masked. A changing batch compiles nothing.

The driver reserves a request's paged KV blocks for its whole `max_tokens` when it opens the sequence, so a running request is never starved and none is preempted. A request that finds no room waits. The loop (`batch/engine.rs`) is the only scheduler: admission, the per-step prefill budget, token commit and delivery. See [Continuous batching](../serve/continuous-batching.md).

**Streaming.** Tokens go out as SSE events through a bounded channel, so a slow client applies back-pressure.

**Sampling.** Greedy, temperature, top-k and top-p [^topp], with logit bias, penalties and logprobs. Every request picks its token on the device, in a step appended to the decode graph. The host reads back the token, a non-finite flag and any top-n logprobs; full logits only on request.

**Guided decoding.** Regex, JSON schema, GBNF grammar, choice lists and forced tool calls constrain sampling with a CPU automaton. The host builds the token mask while the forward pass runs, and the device applies it.

**Speculative decoding** is a driver policy: a decode row proposes drafts (prompt lookup or a second model) and verifies them in one step. `poot-serve` takes it with `--draft-lookup` or `--draft-model`; see [Speculative decoding](../serve/speculative-decoding.md).

## Weights, adapters and multiple GPUs

**Quantized checkpoints.** The library loads one GGUF file or a safetensors directory, and packed projections stay packed. Dense contractions and embedding gathers decode as they consume the weight. A packed MoE expert stack is read by one indexed contraction that decodes only the selected experts.

| Format | Packed on GPU |
| --- | --- |
| GGUF K-quants and Q4_0/Q8_0-style quants [^gguf] | Yes, by default |
| MXFP4 (routed MoE experts) | Packed at load, read in place |
| GPTQ [^gptq], AWQ [^awq] | Packed 4-bit projections by default |
| FP8 (`compressed-tensors`) | Packed E4M3 per-channel projections |

Mixed K-quant files such as `Q4_K_M` widen some layers. KV-cache quantization is not implemented. See [Using quantized checkpoints](../serve/quantized-checkpoints.md).

**LoRA adapters** [^lora] use the PEFT [^peft] layout and are loaded, selected and unloaded while the server runs. They apply to the seven attention and MLP projections of dense decoder families. See [Using LoRA adapters](../serve/lora-adapters.md).

**Tensor parallelism** divides the weights by role and the paged KV pool by KV heads over a group's ranks, over PTX peer-to-peer copies. Only PTX is supported.

- **Verified:** a tensor group and a layer pipeline served requests on a two-GPU NVLink A100 pair, with greedy and sampled output matching single-GPU. World-4 decode matched the single-device oracle on a four-GPU A100 pod.
- **Not covered:** serving a group of four through the server, a real checkpoint, and GPUs reachable only across CPU sockets.

See [Tensor parallelism](../serve/tensor-parallelism.md).

## Metrics

Every value is produced by poot itself, never read from sysfs or a vendor CLI. They cover latency histograms (TTFT, inter-token, end-to-end, queue wait), request and token counters, batching and KV-pool gauges, prefix-cache hit rate, device-memory gauges from the executor's live accounting, and host CPU and memory.

<summary>All metrics by type</summary>

- **Histograms:** `poot_ttft_ms`, `poot_itl_ms`, `poot_request_e2e_ms`, `poot_queue_wait_ms`
- **Counters:** `poot_requests_total`, `poot_requests_completed_total`, `poot_requests_cancelled_total`, `poot_requests_errored_total`, `poot_prompt_tokens_total`, `poot_completion_tokens_total`, `poot_prefix_cache_hit_tokens_total`, `poot_prefix_cache_query_tokens_total`
