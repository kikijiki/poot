# NPU Offload

:::note[Experimental, correctness-scoped]
Two NPUs run a narrow set of programs through the ordinary pipeline: AMD's XDNA2 and Intel's NPU4 (Lunar
Lake). Neither is a serving backend and neither has a `--backend` option: each is a library `Device`
(`poot-npu`, behind its `xdna` feature under the repository's `nix develop .#npu` shell, and its `vpu`
feature under `nix develop .#npu-intel`).

The NPUs are wanted and under active development. The goal is prefill: an NPU produces the KV cache and
another device decodes from it. That handoff is not built yet, and a model served wholly by an NPU is a goal
only if a worthwhile one exists. The generated [feature matrix](../reference/feature-matrix.md) lists which
ops the planner admits for the XDNA2 today.
:::

## What runs

The planner admits each equation for the AIE target. The NPU holds a bounded number of hardware contexts
(16 on this XDNA2) and one loaded artifact takes one, so the compiler groups the planned equations of a
program into **regions**: a contiguous run of equations that is one artifact and one run per step. Each
equation of a region is a Peano core object on its own compute tile; a value only the region's own
equations read moves tile to tile and never reaches host memory, and the region's other tensors sit at fixed
offsets in a few host arenas. A region closes where the next equation would break a measured bound (32
compute tiles, 16 host streams each way, 64512 tile-local bytes). `poot-codegen` links a region with IRON
into an xclbin and instruction stream, the shared `Engine` loads it, and `XdnaDevice` runs it through XRT.
There is no second executor and no graph matcher.

Verified on an AMD XDNA2 NPU (Strix Halo, `aie2p`):

- **Pointwise F32 ops** over dense tensors run as serialized cores: the ordinary kernel body with its
  thread grid turned into loops. Each op has a numerical contract measured on the hardware and checked
  against the CPU oracle over inputs that reach the edges of its domain. Outside the domain nothing is
  promised.
  - `add` and `sub`: within 2 x 2^-23 of the larger operand (the core's adder is not round-to-nearest-even;
    a cancellation that leaves a small result is exact). Domain: finite operands with a finite normal result.
  - `mul`, `div`, `neg`, `recip` and `ge`: bit for bit equal to the IEEE result. Domain: finite operands with
    a finite normal result.
  - `exp`: absolute error 2e-6 plus relative 1e-5. Domain: -87 to 88. The core clamps its argument to
    +-88, so larger arguments saturate instead of overflowing.
  - `log`: the same bound. Domain: positive normal numbers (from 1.18e-38 up); smaller inputs are not
    promised.
  - `tanh` and `erf`: the same bound over every finite input, which they saturate exactly.
  - `sqrt`: relative error 4e-7, the core's software square root (a bit-halving estimate and four Newton
    steps). Domain: positive normal numbers.
  - `max`: the larger operand, exactly (a compare and select). Domain: operands that are not NaN.
  Activation slots and a carried running-sum state replay over changing inputs.
- **Row reductions and norms** run as the ordinary row kernel with one lane per row, its row loop serialized
  like the pointwise ones: no workgroup memory and no barrier.
  - A last-axis `sum` adds in order and is within `2 x cols x 2^-23` of the sum of the row's magnitudes (each
    addition is faithful to two units of its larger operand, and a sum that cancels has no relative bound).
    A last-axis `max` is exact.
  - A fused norm (RMSNorm, with or without a weight) has a bound derived from its steps: `mul` and `div`
    are exact, an `add` is admitted only when both operands are provably non-negative (it cannot cancel), a
    `sqrt` only when its operand is provably a positive normal number, and a `sum` only over non-negative
    terms. The derived relative bound of a 64-column RMSNorm is 8.5e-6, and the hardware stays under
    3 percent of it. A step with no derived bound (a subtraction, `exp` inside a row kernel, a signed `sum`) is
    a typed refusal that names the missing bound, so a LayerNorm and a softmax are refused.
- **Gather** of `F32` or `I32` elements through an `I32` index returns the source elements bit for bit,
  negative zero and NaN payloads included, along any axis. An index outside the axis is not checked, as on
  the GPU kernel.
- **A graph of twenty equations with twenty distinct shapes runs in three hardware contexts**, where one
  artifact per equation fails at the seventeenth load.
- **Region bounds, measured**: 32 compute tiles, 16 host streams in and 16 out, 2 streams per tile, and a
  tile-local limit of 64512 bytes. An artifact at each bound links and runs, and one past it is refused by
  the toolchain; the compiler splits a program at these numbers, or refuses an equation that fits no region
  with a typed limit.

Nothing else is verified. Every other equation (`erf`, other unary ops, reductions over another axis or
another element type, data movements other than gather, matmul, attention, collectives) is refused by the
planner with a typed capability, and no model runs on the NPU. Performance
is not a goal of this path: it is scalar, and not competitive with the GPU backends.

## Intel NPU

An Intel NPU has no public core ISA or kernel toolchain. Its only entry point is the driver's graph compiler,
so the artifact of a program is one **graph**: the planner lowers each equation to the one OpenVINO opset op
with the same semantics (`add`, `subtract`, `multiply`, `divide`, `maximum`, `greater-equal`, `exp`, `negative`, `sqrt`,
`reduce-sum`, `reduce-max`, `matmul`, `gather`, `reshape`, `transpose`, `broadcast`, `slice`, `concat`,
`convert`, a constant range for `iota`, and a scatter for `dynamic_update_slice`; an inline scalar literal
becomes a constant) and nothing is recognized as a composite, so attention stays its
primitives and the vendor compiler fuses what it can. `poot-codegen` serializes the whole program as OpenVINO
IR, the shared `Engine` hands it to `VpuDevice`, the driver's compiler builds the blob, and the device runs
the graph through Level Zero. Every value the graph's own equations read stays inside it; its arguments are
the weights, activations and state it reads and the values it returns, in host memory the NPU addresses.

The NPU computes in FP16, and a vendor compiler handed an F32 graph narrows it silently, so poot makes the
narrowing a step of its own. When the device records a numerical contract (a bound on the normwise error of a
narrowed region, measured on the device against the F32 CPU oracle), `compile` rewrites the graph itself
(`narrow_to_device_precision`, the first pass for this target): each F32 argument is converted to FP16 by an
explicit `Cast` equation on entry, the whole graph computes in FP16 and each F32 result is converted back by a
`Cast` on exit; nothing in between is converted op by op, so the contract bounds the graph's error as a whole.
The casts are ordinary equations, so the program's published numerics class sees the narrowing: it is
`NarrowStorage`, the loosest comparison tolerance, and a result is compared against the oracle within it. A target that
records no contract refuses an F32 arithmetic equation with a typed capability naming the missing contract,
and BF16 arithmetic, which no contract covers, is refused as well. Data movement is bit exact in any width the
device carries.

The contract's bound holds only for values FP16 can hold, so the contract also records the largest magnitude an
F32 value may have (65504). A literal beyond it is refused when the graph is planned, except the additive
literals described below, which saturate on purpose. The device checks F32 values where the host can see
them. A weight is checked once, as it is uploaded: a weight beyond the range, or a NaN, is refused with
`NarrowingRangeUpload`, which names the element, before any replay exists, and no replay reads it again. The
graph's other F32 inputs are checked before each replay: a value beyond the range, or a NaN, is a typed
error that names the argument and the element and runs nothing. An argument that an earlier command of the
same recording writes is checked as that command's result instead, and so is a weight a recorded copy fills. The F32 results
are checked after the replay too, since a result that left the range was computed outside what the bound was
measured on. On the laptop NPU an F32 input of 65504 runs, an input of 65520 (which FP16 rounds to infinity)
is refused, and a sum of two in-range inputs that exceeds the range comes back as a finite F32 and is refused
as a result.

Compiled blobs are cached on disk under the region's full identity (the part, the vendor compiler's version,
the compiler options and the IR with its constants), so a second run of the same program loads the blob and
never runs the compiler. A cache entry that is damaged, truncated or another region's, or that the driver
refuses, is recompiled and replaced.

Verified on an Intel Core Ultra (Lunar Lake) NPU, driver and compiler 1.38.0:

- **F16 programs** over elementwise `add`, `sub`, `mul`, `max`, `ge`, `div`, `neg`, `sqrt` and `exp`, inline
  scalar literals, row and column sums and maxima, a matmul, a gather by `I32` indices (also by an `iota`),
  transpose, reshape, slice, concat and broadcast, a `dynamic_update_slice` at a literal and at a runtime
  index, rank four tensors, an `F32` boundary around FP16 arithmetic, activation slots, a carried running-sum
  state, and replay over changing inputs match the CPU oracle bit for bit on integer-valued inputs and within
  FP16 tolerance for `exp`, `div` and `sqrt`. The sign of a zero is not promised: the NPU's `neg` of `+0` is
  `+0`.
- **A program is one compiled graph and one replay per step**, however many equations it holds.
- **The compiled graph's arguments are checked against the program's** (names, order, direction, extents,
  precision) before anything runs, so a compiler that reordered, retyped or reshaped an argument is a typed
  refusal.

Nothing else is verified. Every other equation is refused by the planner with a typed capability: `log`,
`recip` and the other unary ops, BF16 arithmetic and F32 arithmetic on a target with no recorded narrowing
contract (the NPU computes in FP16), and converts through BF16 or an integer. Softmax, attention and
collectives are not recognized as composites, and no model runs on the Intel NPU. A literal FP16 cannot hold
is refused (`NarrowingRange`), unless the target records the narrowing contract and the literal is the operand
of an add or subtract: then a finite F32 literal saturates to +/-65504 (a mask sentinel acting as an infinity).
A multiplicative use stays refused, an infinite literal stays infinite and a NaN literal is refused. An integer
converted to a float is refused as `IntegerToFloat`, because FP16 holds integers exactly only up to 2048. The
index of a runtime `dynamic_update_slice` must select a window that fits: the CPU oracle rejects an
out-of-range index with a typed error, but the NPU does not check it and its result is undefined. A layer the
vendor compiler rejects is a typed error carrying the compiler's own log. Performance is not a goal of this
path.

## Failure behavior

Dispatch refusals that need no hardware (a grid launch, a stream or buffer that is not the kernel's shape
ABI) are typed errors before XRT is touched. A run that misses its deadline is a typed error and poisons the
device; the buffers and host arenas it used stay allocated until the device is dropped. The Intel device
behaves the same way: its dispatch refusals (a grid launch, an invocation of another graph, a buffer that is
not the graph's argument) are typed errors before Level Zero is touched, and a replay that misses its deadline
poisons the device and keeps the failed recording's buffers alive until it is dropped.
