# NPU Offload

This page states what the two experimental NPU devices run, with their numerical contracts and refusals.

:::note[Experimental, correctness-scoped]
AMD's XDNA2 and Intel's NPU4 (Lunar Lake) each run a narrow set of programs through the ordinary pipeline. Neither is a
serving backend or a `--backend` option. Each is a library `Device` in `poot-npu`:

- XDNA2: the `xdna` feature, under `nix develop .#npu`.
- Intel: the `vpu` feature, under `nix develop .#npu-intel`.

Planned: prefill on an NPU, with another device decoding from its KV cache. That handoff is not implemented. The generated
[XDNA2 table](../develop/supported-models.md#xdna2-npu) lists the ops the planner admits.
:::

## AMD XDNA2

### How a program runs

The NPU has a bounded number of hardware contexts (16 on this XDNA2), and one loaded artifact takes one. The compiler groups
planned equations into **regions**, each one artifact and one run per step.

- Each equation is a Peano core object on its own compute tile.
- Values read only inside the region move tile to tile and never reach host memory.
- A region closes where the next equation would break a measured bound:

| Bound | Limit |
| --- | --- |
| Compute tiles | 32 |
| Host streams | 16 in, 16 out, 2 per tile |
| Tile-local bytes | 64512 |

An artifact at a bound links and runs; one past it is refused by the toolchain. The compiler splits a program there, or refuses
an equation that fits no region with a typed limit. Twenty equations with twenty distinct shapes run in three contexts.

`poot-codegen` compiles each core with Peano, `poot-npu` links a region with IRON into an xclbin and instruction stream, the
shared `Engine` loads it, and `XdnaDevice` runs it through XRT. There is no second executor and no graph matcher.
`poot-npu-artifacts` holds the host side of a compiled artifact (XDNA2 and Intel); the planner and engine know no vendor.

### Verified: pointwise F32 ops

Pointwise ops run as serialized cores: the ordinary kernel body with its thread grid turned into loops. Each contract was
measured on hardware against the CPU oracle; outside the domain nothing is promised. Activation slots and a carried running-sum
state replay over changing inputs.

| Op | Contract | Domain |
| --- | --- | --- |
| `add`, `sub` | Within 2 x 2^-23 of the larger operand (the adder is not round-to-nearest-even). | Finite operands, finite normal result |
| `mul`, `div`, `neg`, `recip`, `ge` | Bit for bit the IEEE result. | Finite operands, finite normal result |
| `exp` | Absolute 2e-6 plus relative 1e-5; the argument clamps to +-88. | -87 to 88 |
| `log` | Same bound. | Positive normal numbers |
| `tanh`, `erf` | Same bound; they saturate exactly. | Every finite input |
| `sqrt` | Relative 4e-7 (software: bit-halving estimate, four Newton steps). | Positive normal numbers |
| `max` | The larger operand, exactly. | Operands that are not NaN |

### Verified: reductions, norms and gather

Row reductions and norms run as the ordinary row kernel, one lane per row, with no workgroup memory or barrier.

- **Last-axis `sum`:** adds in order, within `2 x cols x 2^-23` of the sum of magnitudes. **`max`:** exact.
- **Fused RMSNorm** (with or without a weight): bound derived from its steps; 8.5e-6 relative for 64 columns, and the hardware
  stays under 3 percent of it.
- **Gather** of `F32` or `I32` through an `I32` index returns source elements bit for bit, along any axis. An index outside
  the axis is not checked.

A norm step is admitted only with a derived bound:

| Step | Admitted when |
| --- | --- |
| `mul`, `div` | Always (exact) |
| `add` | Both operands provably non-negative |
| `sqrt` | Operand provably a positive normal number |
| `sum` | Over non-negative terms |

A step with no derived bound (subtraction, `exp` in a row kernel, a signed `sum`) is a typed refusal naming the missing bound,
so LayerNorm and softmax are refused.

### Not verified

Every other equation is refused with a typed capability: other unary ops, other-axis reductions, data movement other than
gather, matmul, attention, collectives. No model runs on the NPU, and performance is not a goal.

## Intel NPU

Intel NPUs have no public core ISA, so a program's artifact is one **graph** built by the driver's graph compiler.

1. The planner lowers each equation to the OpenVINO opset op with the same semantics. Nothing is recognized as a composite.
2. `poot-npu` serializes the program as OpenVINO IR; `VpuDevice` has the driver build the blob and runs it through Level Zero.
3. Values read only inside the graph stay inside it. Arguments (weights, activations, state, results) live in host memory.

Lowered ops: `add`, `subtract`, `multiply`, `divide`, `maximum`, `greater-equal`, `exp`, `negative`, `sqrt`, `reduce-sum`,
`reduce-max`, `matmul`, `gather`, `reshape`, `transpose`, `broadcast`, `slice`, `concat`, `convert`, `iota` (a constant range)
and `dynamic_update_slice` (a scatter). A scalar literal becomes a constant.

### FP16 narrowing

The NPU computes in FP16, and a vendor compiler narrows an F32 graph silently. poot makes narrowing an explicit step. When the
device records a numerical contract (a normwise error bound measured against the F32 CPU oracle), `compile` runs
`narrow_to_device_precision`, the first pass for this target:

1. Each F32 argument gets a `Cast` to FP16 on entry.
2. The whole graph computes in FP16.
3. Each F32 result gets a `Cast` back on exit.

The contract bounds the graph as a whole, and the program's numerics class is `NarrowStorage`, the loosest tolerance.

| Case | Outcome |
| --- | --- |
| F32 arithmetic, no recorded contract | Typed capability error naming the missing contract |
| BF16 arithmetic | Refused; no contract covers it |
| Data movement | Bit exact in any width the device carries |

### Range checks

The contract holds only for values FP16 can hold, so F32 magnitudes are limited to 65504.

| Value | Checked | On failure |
| --- | --- | --- |
| Literal | At planning | `NarrowingRange`, except additive literals (below) |
| Weight | Once, at upload | `NarrowingRangeUpload`, naming the element |
| Other F32 inputs | Before each replay | Typed error naming argument and element; nothing runs |
| F32 results | After each replay | Typed error |

NaN weights and inputs are refused. An input of 65504 runs; 65520 (which rounds to infinity) is refused; a sum of in-range
inputs that exceeds the range is refused as a result. An additive literal (an add or subtract operand) with a recorded contract
saturates to +-65504, a mask sentinel acting as infinity. Multiplicative use stays refused, infinite literals stay infinite,
and NaN literals are refused.

### Blob cache

Blobs are cached on disk under the region's full identity: part, vendor compiler version, options, and the IR with constants. A
repeat run never invokes the compiler. A damaged, truncated, foreign or driver-refused entry is recompiled and replaced.

### Verified and refused

Verified on an Intel Core Ultra (Lunar Lake) NPU, driver and compiler 1.38.0:

- **F16 programs** over the lowered ops (elementwise, reductions, matmul, gather, layout ops, `dynamic_update_slice`, rank four
  tensors, an `F32` boundary around FP16 arithmetic, activation slots, carried state, replay over changing inputs) match the
  CPU oracle bit for bit on integer-valued inputs and within FP16 tolerance for `exp`, `div` and `sqrt`. The sign of a zero is
  not promised (`neg` of `+0` is `+0`).
- **One compiled graph and one replay per step**, however many equations.
- **Arguments are checked** against the program's (names, order, direction, extents, precision) before anything runs.

Refused with a typed capability (no model runs on the Intel NPU; performance is not a goal):

- `log`, `recip` and other unary ops.
- BF16 arithmetic, and F32 arithmetic with no recorded contract.
- Converts through BF16 or an integer; integer to float is `IntegerToFloat`, since FP16 holds integers exactly only to 2048.
- Softmax, attention and collectives.
- A layer the vendor compiler rejects, with the compiler's log.

The index of a runtime `dynamic_update_slice` must select a window that fits. The CPU oracle rejects an out-of-range index; the
NPU does not check it, and its result is undefined.

## Failure behavior

- Dispatch refusals that need no hardware are typed errors before XRT or Level Zero is touched: a grid launch, a buffer that is
  not the kernel's shape ABI (XDNA2), an invocation of another graph, a buffer that is not the graph's argument (Intel).
- A run that misses its deadline is a typed error and poisons the device. Its buffers stay allocated until the device drops.
