# NPU Offload

:::note[Experimental, correctness-scoped]
The AMD XDNA2 NPU runs a narrow set of programs through the ordinary pipeline. It is not a serving
backend and has no `--backend` option: it is a library `Device` (`poot-npu`, behind its `xdna` feature,
built under the repository's `nix develop .#npu` shell). Intel NPUs are not supported.
:::

## What runs

The planner admits an equation for the AIE target, `poot-codegen` compiles it to a Peano core object and
links it with IRON into an xclbin and instruction stream, the shared `Engine` loads that artifact, and
`XdnaDevice` runs it through XRT. There is no second executor and no graph matcher.

Verified on an AMD XDNA2 NPU (Strix Halo, `aie2p`):

- **F32 `add`, `sub` and `mul`** over dense tensors, run as one sequential core, match the CPU oracle bit
  for bit on integer-valued inputs and within 1e-5 on fractional ones, including activation slots and a
  carried running-sum state, replayed over changing inputs.
- **Tile-local limit: 64512 bytes**, measured. An add whose double-buffered FIFOs reserve exactly that runs;
  one element more per binding is refused before linking as a typed limit.

Nothing else is verified. Every other equation (unary ops, `max`, `div`, reductions, matmul, attention,
collectives) is refused by the planner with a typed capability, and no model runs on the NPU. Performance
is not a goal of this path: it is scalar, one core, and not competitive with the GPU backends.

## Failure behavior

Dispatch refusals that need no hardware (a grid launch, a stream or buffer that is not the kernel's shape
ABI) are typed errors before XRT is touched. A run that misses its deadline is a typed error and poisons the
device; the buffers it used stay allocated until the device is dropped.
