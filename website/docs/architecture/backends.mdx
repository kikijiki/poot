# Backends

poot has four GPU backends built from one kernel source. The AMD XDNA2 and Intel NPU4 NPUs are experimental `Device`s (see [NPU Offload](./npu.mdx)). The CPU oracle is a test-side reference, not a backend.

<BackendDiagram />

| Backend | Codegen target | Compiler | Artifact | Runtime per token | `Device` |
| --- | --- | --- | --- | --- | --- |
| **wgpu** (portable default) | `SpirvVulkan` | `llc` | SPIR-V | Cached command buffer, re-encoded | `WgpuDevice` |
| **Raw Vulkan** (SPIR-V through `ash`) | `SpirvVulkan` | `llc` | SPIR-V | Command buffers recorded once, replayed | `VulkanDevice` |
| **ROCm** (AMD, raw HSA) | `AmdGcn(arch)` | `clang` (amdgcn-amd-amdhsa) | HSACO | HSA AQL packet replay | `RocmDevice` |
| **PTX** (NVIDIA) | `Nvptx` | `llc` (nvptx64, sm_80) | PTX | CUDA graph replay through [cudarc](https://github.com/coreylowman/cudarc) | `PtxDevice` |

Everything from model definition through graph IR, fusion and planning is backend-neutral. Backends diverge late: the planner picks a kernel specialization from the caps the device reports (what a target cannot run is a planner refusal, not an executor branch), `poot-codegen` chooses address spaces, intrinsics and atomics per target, and the runtime dispatches differently.

All four implement one executor contract: `poot-executor`'s generic `Engine<D>` over a thin `Device` trait, checked by the table-driven `poot-executor-parity` crate. See [Execution](./execution). `AieCore` codegen produces a linked artifact for an NPU region, loaded by `poot-npu`.

## wgpu (SPIR-V)

Runs on any Vulkan-capable GPU, integrated ones included, with no vendor SDK. Verified on AMD Radeon (RADV) and Intel Arc iGPUs. Cached graph execution reuses pipelines and bind groups and re-encodes dispatches per token.

SPIR-V targets (wgpu and raw Vulkan) have no grid-wide sync or cooperative kernels, need structured control flow (a structurization pass runs before emit), ban private arrays with dynamic indices (use workgroup LDS), and have no bf16 on most iGPUs, so compute is f32.

## Raw Vulkan (SPIR-V)

`poot-vulkan-runtime` dispatches the same `.spv` as wgpu with the same binding ABI, so a kernel runs unmodified on either. `VulkanDevice` records a step once and resubmits it per token.

- **Faults.** A failing kernel check sets a bit in the dispatch's error word, and `synchronize` raises it as a typed fault. SPIR-V has no trap, so the runtime requires `robustBufferAccess`.
- **Timeouts.** Each fence wait is bounded (600 seconds by default). A timeout or a failed submission poisons the device and refuses every later operation.
- **Serving** needs `VK_EXT_memory_budget`.
- **Selection.** `--backend vulkan` asks for it; `--backend auto` never picks it, since it is the same hardware as wgpu's adapter ([Picking a backend](../serve/choosing-a-backend.md#supported-backends)).
- **Not available:** collectives, multi-GPU, and device time (`--device-timing` reports `null`).

Verified on the AMD Strix Halo iGPU under RADV only.

## PTX (NVIDIA)

The decode dispatch sequence is captured once into a CUDA graph and replayed per token with one `cuGraphLaunch`. Kernel arguments point at stable slot buffers the host rewrites in place.

PTX can also drive several GPUs from one executor as a layer pipeline: each stage is its own CUDA graph on its own device, and activations crossing a stage boundary are copied peer to peer. Only point-to-point transfers are supported; reductions and gathers are refused. This is not used for serving.

Verified on NVIDIA L40S through rented pods.

## ROCm (AMD)

ROCm talks to the GPU through raw HSA, not HIP math libraries; poot supplies every kernel. The HSA library is loaded at run time, so ROCm is in every build and `--backend rocm` needs no build flag.

With no vendor graph API, poot records the dispatch sequence as AQL packets and resubmits them per token. Paged KV and flash attention are hardware-verified on AMD Radeon 8060S (gfx1151) and gfx1100.

## Sampling and precision

On every backend the next token is picked on the device, in a step appended to the decode graph. The host reads back the token id, a non-finite flag and any logprobs; bias, penalties and the guided mask run in that step. See [Serving design](./serving-design.mdx#the-scheduling-loop).

What a backend can run is decided by planning: a graph runs when `compile` succeeds for that target, and a refusal names the op and the missing capability. [Supported models and formats](../develop/supported-models.md) is generated from those results.

| | wgpu, raw Vulkan | ROCm | PTX |
| --- | --- | --- | --- |
| Compute dtype | f32 | f32, opt-in bf16 matmul | f32, opt-in bf16 matmul |
| Matrix unit | Not used: every GEMM is the register-tiled body on the vector units | Not used | Not used |

## Correctness

Every backend is checked against the CPU oracle (`poot-eval`): executor tests dispatch kernels with identical inputs and compare. `ptx-check` and `rocm-check` do the same on real hardware, and fail when they find no fixture. `poot-vulkan-check` is a one-kernel smoke check of the raw Vulkan runtime. See [Execution](./execution#verification).
